## 三、对实现方案的直接影响（写进 proposal）

1. **三个端点都归入「判定/短答复类」**：走应用既有的 `thinking` 关闭路径（`ai_client.py` 的 `_with_thinking_disabled` + 端点拒绝时的去掉重试），`max_tokens` 用默认档（1024）即可，不需要为 JSON 留超大预算。
2. **多样性靠「明面字段」而不是靠祈祷**：`focus` 必填 + 「结构上真的不同，想不出三套给两套」这条规则实测有效；实现时把 `focus` 去重与 spine 相似度做成**代码侧软校验**（便宜、能拦住退化的那一轮）。
3. **规则 7 的产出就是 `checks`**：实测模型会主动报告「我与作者那句话的张力」，前端那条自查条不是装饰。
4. **体检的 `none` 组是设计内的**：没有章节时它老实占位，不需要在 P0 做「对已写内容」的真检查（P1 再补）。
5. **我的「疑似新造名词」启发式不可用**（字段名碎片全是误报）；真实现应改为**实体名对拍**：输出里出现的专有名词必须能在角色表/世界设定/全景里找到，找不到的才标记。

## 四、这次没覆盖的（下次补）

- 单本书、单模型（`deepseek-v4-flash`）、每模板仅 2 次；未测 GLM 与更强的 `deepseek-v4-pro`。
- 未测「主线很薄」（全景只有一两句）的极端样本——那是编造风险最高的一档。
- 体检用的是 expand 刚产出的卷纲（一致性天然高）；未测「故意写歪的卷纲」是否能被 warn 抓到。
- 未测多卷连续（第二卷的「上一卷结尾＝事实优先」取数）。
