## 1. 现状 vs 目标

| | 现行（排队顺延） | 目标（升级补差） |
|---|---|---|
| 触发人群 | 囤套餐 / 提前续费 | 用得好想换更高档 |
| max 起算 | pro 到期日（`calc_grant_start` = max(active 最远到期, 今天)） | **支付成功即刻** |
| pro 剩余 20 天 | 原样跑完 | 折成价值抵扣差价，pro 行终止 |
| 用户感知 | 「我买了 max 怎么还是 pro」 | 立刻变 max |

两条路并存不互斥：普通购买仍走排队顺延（红线不动），升级是新增的独立链路。

## 2. 核心语义（拍板项 1，PM：同意）

**升级 = 到期日不变，把剩余时长从低档换成高档，按秒补差价。**

- pro 到期日 = 20 天后 → 升级后 max 的 `expires_at` 仍是那一天
- max 行 `grant_start` = 支付确认时刻（秒级）
- 用户为「剩余 20 天的 pro→max 品质差」付费，不多买时间不少买时间

不采用「max 从今天重算一个完整周期」——那不是补差价，是补差价+送时间，账对不上。

## 3. 差价公式（纯函数 `calc_upgrade_quote`，落 domain/payments/pricing.py）

```
rem_sec     = pro行.expires_at − now                      （秒）
max_sec_pr  = max SKU 实付单价 / (period_days × 86400)     （现价，含现折扣）
pro_sec_pr  = pro行.原单amount_fen / (period_days × 86400) （原单实付，含历史折扣）
credit_fen  = round_half_up(pro_sec_pr × rem_sec)          （pro 剩余价值抵扣）
list_fen    = round_half_up(max_sec_pr × rem_sec)          （剩余时长的 max 全价）
pay_fen     = list_fen − credit_fen                        （应付差价，恒 > 0 因高档秒价更高）
```

- pro 基价用**原单实付**而非现价：用户当时花多少钱就折多少（拍板项 2，PM：同意——没付过的钱不能折出价值，且封死「折价买入、全价折抵」套利）
- credit/list 各自先取整再相减，与退款的 `_round_half_up` 同族，对账清晰
- 逆序（目标档 rank ≤ 当前档）拒绝走升级链路
- **目标档周期 = 当前套餐周期**（拍板项 10，PM：同意）：升级不跨周期——剩余时长/到期日继承当前套餐，目标 SKU 恒取「与当前套餐同时长」的档位现价秒折。包年秒价虽更低但与升级无关（到期日后重新购买才是新周期）。原型已演示两价并存自洽
- 实例（pro ¥30/30天、max ¥60/30天，用 10 天剩 20 天）：credit = 2000 分（¥20.00）；list = 4000 分（¥40.00）；**应付 = ¥20.00**

### 3.1 选购页价格联动 + 续费/升级双入口（拍板项 8/9）

处于生效期低档的用户打开选购页（CashierPage 态一，选套餐区）：

**卡片价格（拍板项 8，PM：有条件同意，条件已折入）**

- **更高档卡片的主展示价 = 按页面打开时刻算出的补差价**（pro 用 10 天 → max 卡主价 ¥20），续费全价降辅助信息
- **升级价只在时长 tab = 当前套餐周期时展示**（P1-2）；其余 tab 下高档卡回归全价卡——「升级行/续费行/卡头天数」三个时间量纲同卡是认知陷阱
- 页面价是**打开时刻的预估**：下单进收银台按下单时刻重算，**以收银台为准**（停留几分钟漂移 ≤ 分币级）
- `GET /api/payments/upgrade-quote` 一次批量返回所有可升高档位的 quote（页面一次拉取，逐卡渲染）

**下单双入口（拍板项 9，PM：同意）**——底部购买条按所选档与当前生效档的关系分三态：

| 用户状态 | 所选档 | 购买条 |
|---|---|---|
| 生效期低档（pro 计时中）+ 同时长 tab | 更高档（max） | **双按钮**：主「升级 · 立即生效 ¥20」+ 副「续费 ¥60（到期后接续）」 |
| 同档（pro 看 pro） | 同档 | 单「去支付 ¥30」（续费=排队，现状不变） |
| 免费 / 无生效行 | 任意 | 单「去支付」（现状不变） |
| 低档已被降级守卫拦截 | — | 现状不变 |

- **升级按钮** → upgrade 单（order_kind=upgrade + base_code_id，差价金额）；付完**自动换档**，态三文案「已升级，计时中」，无「立即激活/先存着」分支
- **续费按钮** → 现有 create_order 全价链路原样走（排队顺延 + 态三「立即激活/先存着」），一根手指不动
- 两个按钮都复用同一个微信扫码收银台（态二），只是下单端点与金额不同

**升级入口守卫（缺一不可，命中即隐藏入口）**：

| 守卫 | 依据 |
|---|---|
| base 行必须「计时中」（grant_start ≤ now < expires_at） | 排队未起算行不参与升级 |
| base 行 source 必须为 'order'（P1-3） | 手工码无「原单实付」可折，v1 直接不展示入口，砍掉整类边界 |
| base 行所属订单不在退款流程中（P0-3） | refund_pending / refund_processing 期间禁升级——否则换档 superseded 拒退会吞掉用户已确认的退款 |
| base 行无 pending 升级单（P1-4） | 同一 base 行重复挂单：拒绝新单，文案「您已有一笔待支付的升级订单」（推荐拒绝而非作废旧单，防死码） |
| 无排队中同档或更高档行（P2-1） | 提示文案**分两情形**：同档排队→「您已有 MAX 排队中，到期后将自动接续」；更高档排队→「您已有更高档套餐排队中」。v1 拦截、后续可按支持信号重开（排队叠加升级的账目已验算可行，见 §9） |

## 4. 台账与状态机（本体论：动作作用于被升级行，引用合法拥有）

```
pro 行:  active ──CAS──▶ superseded（新终态；expires_at 不动，记 superseded_by=max行code_id）
max 行:  新建 pending_activation ──CAS──▶ active（grant_start=now秒级, expires_at=继承原到期日）
```

- `grant_start/expires_at` 表列本就是 datetime，升级链写**秒级时刻**（naive UTC），与退款折算口径一致；普通购买仍是 0 点粒度，互不影响
- 双 CAS 顺序：**先 max 行起算、后 pro 行截断**。中途崩溃 = 短暂双活（多给几秒，可接受），反向会断档（不可接受）
- 自愈：T2 补偿扫描重放换档；pro 行未截断的半截态由事件 `codes.upgraded` 对账补截
- **「我的套餐」页口径（P1-1）**：superseded 行**不出现在套餐明细**（grants 查询排除，不进 pending/active/revoked 三态 tab——映射进「已收回」会把主动升级显示成惩罚性词汇）；升级历史只在订单侧可见（升级单+原单各自留痕）。`GET /pay/license/grants` 的排除逻辑在 spec delta 显式裁定（s-pay-account-views）
- superseded 退出其余 active 口径零改动自动正确：`resolve_effective_tier`、排队 `find_active_by_user_id`、注销 R2 阻塞清单、退款收回扫描——全部按 `status='active'` 过滤

### 4.1 数据设计：三张表各司其职（零 DDL 实细节）

**两单关联 = 单向、冻结在下单瞬间**：升级单 `sku_snapshot.upgrade.base_order_no` 指向 PRO 原单；PRO 原单不回指升级单（避免双向同步）。全链只有这一个关联字段。

**时机一：支付成功换档（fulfill 内）——PRO 订单行一字不动**

| 表 | 行 | 写什么 |
|---|---|---|
| orders | 升级单（新行） | 正常 pending→paid→fulfilled；sku_snapshot 冻结 upgrade 块（base_order_no/credit_fen/list_fen/rem_sec/base_expires_at） |
| codes | PRO 行 | CAS active→superseded（expires_at 不动）；max_code_id 关联**不落列**，落 trade_events：`codes.superseded`（payload 带 new_code_id + upgrade_order_no）与 MAX 行 `codes.activated`（payload 带 base_code_id）双向可溯 |
| codes | MAX 行（新行） | create_from_order 照常，grant_start=秒级 now、expires_at=继承、order_id=升级单 id |
| orders | PRO 原单 | **不动**（钱、状态、退款列全不动——动作只作用于 codes 台账行） |

**时机二：退款提交（R3）——一个退款实体 + 两条腿（地基=A 册 refunds/refund_legs 表）**

| 表 | 行 | 写什么 |
|---|---|---|
| refunds | 实体行 | refund_no、status 走 cooldown→processing→succeeded、initiated_by_order_no=升级单号、total_fen=due（合计应退） |
| refund_legs | 腿A | 升级单号 + amount_fen=legA + 微信退款单号 + refunded_at |
| refund_legs | 腿B | PRO 原单号 + amount_fen=legB + 微信退款单号 + refunded_at |
| orders ×2 | 派生缓存 | refund_status/金额/refund_reason 同批更新——仅列表筛选与行展示消费，域真相在实体 |
| codes | MAX 行 | 冻结照旧（实体流程内的 frozen）；PRO 行已 superseded 无可冻 |
| trade_events | 实体挂账 | 提交事件带 refund_no + `{legs:[...]}`，两腿原子留痕 |

- **主动/被动退款查询口径**：PRO 原单的被动性=「有腿、无发起」（腿由实体连带执行、订单无 requested_at）+ 缓存 refund_reason='superseded_by_upgrade'——订单详情据此显示"已退款 ¥16 · 套餐升级折抵"并拒退新申请
- **金额口径双轨守卫（IA 评审 P0-1）**：按"一笔退款"计量的界面（首页横幅/退款流程页/详情时间线）一律读实体 total_fen（¥36）；按订单行计量的（订单列表行）一律读本单腿金额（¥20/¥16）——混用即双计或短计，两行都显示 ¥36 会被读成退了 ¥72，红线
- T4 对账：微信账单两笔退款按 out_refund_no 各自归位自己订单（legs 匹配），按订单聚合现逻辑兼容
- B 册本体零 DDL 依旧成立（升级单指向走快照；腿表由前置 A 册交付）

## 5. 订单链路复用（零 DDL）

- `orders` 表不加列：`order_kind: "upgrade"` 放进 `sku_snapshot` JSON（拍板项 7，PM：同意——生产 PG 手工维护，能零 DDL 就零 DDL；代价=指标查询走 JSON 提取，当前量级可接受）
- 快照新增：`{order_kind, upgrade: {base_code_id, base_order_no, rem_sec, credit_fen, list_fen, base_expires_at}}`
- 金额 `amount_fen` = pay_fen，微信 Native 出码、回调、对账、T1 关单全部复用现链路
- **快照冻结，支付确认时不重算**（拍板项 6，PM：同意——付费须知 §三.2「订单创建时价格即锁定」背书；状态突变由下方守卫兜住）
- fulfill 分支：upgrade 单发货 = 幂等插 max 行 + **自动执行换档**（不用用户再点激活——升级要「尽快兑现」）
- **P0 守卫（换档 CAS 前逐项校验 base 行，任一失败 → 订单自动全额退款 + max 行置 revoked + 事件留痕；收了钱没兑现必须退）**：
  1. base 行仍 active 且未到期（挂单期间到期）
  2. base 行不在退款流程中（P0-3：所属订单 refund_status ∉ {refund_pending, refund_processing}）
  3. base 行未被并发升级（仍非 superseded）

## 6. 退款与冷静期（PM 评审 P0 主战场，整体重写）

### 6.1 两腿退款（P0-1，资金流硬约束）

**微信退款 API 的累计退款不能超过该单实付**——升级单实付只有 ¥20，一笔订单物理上退不出等效实付 ¥40。等效实付是**记账恒等式**，资金流必须拆两腿：

```
due  = round_half_up(list_fen × rem_R / rem_T)   （应退合计；rem_T=升级时刻剩余秒，rem_R=退款确认时刻剩余秒）
legA = min(due, pay_fen)                          （腿A=升级单原路退，封顶升级单实付）
legB = min(due − legA, credit_fen)                （腿B=PRO 原单原路退，封顶折抵额）
```

- 用户侧展示**合计应退**（两笔各自原路退回）——refund 页两腿明细已入原型（refund.html 态七/态八）
- 腿B 走 PRO 原单：其未退余额 = 原单实付 − 0 ≥ credit_fen 恒成立（credit 本就是按秒折出的剩余价值）；腿B 金额随时长自然衰减，不受快照冻结影响
- **退款对象归属（09-07 拍板：退款升格为独立域实体，推翻 08-29「不设独立退款单」的域模型层；UI 呈现经 PM 评审裁定不变）**：本场景退款=**一个 refund_no 实体 + 两条资金腿**。属主单=升级单（用户从它发起）；流程状态（申请/确认/冻结/冷静期/取消）全挂实体；腿A→升级单、腿B→PRO 原单，每腿各自记录金额与微信退款单号，只是资金执行明细。PRO 原单无申请入口（`superseded_by_upgrade` 拒退），其腿由实体流程连带执行；「每笔订单仅办理一次退款」=每单至多一条有效腿，逐单成立。冷静期取消=整实体取消、两腿都不提交，不存在「退了一半」；升级守卫已保证 PRO 原单从未退过款（退过则行非 active 进不了升级），腿B 余额必然充足。微信侧两笔调用各以自己订单号为 out_refund_no 互不撞号。**前置依赖：A 册《退款实体升格》先落（§12 立项顺序）**
- **PRO 原单不可被单独发起退款**（新拒退原因 `superseded_by_upgrade`：剩余价值已转让给升级行）；腿B 只能由升级单退款流程连带触发——一次申请、一个流程、两笔原路，与《退款政策》「每笔订单仅办理一次退款」兼容（两笔=两笔订单各一次）
- 实现：refund.py 的 `min(refund_fen, amount_fen)` 单腿封顶是存量假设，两腿拆分落 refund_flow.py；`REASON_SUPERSEDED` 保留（防升级后再对 superseded 行发退款）
- 两腿同流程同节奏：确认 → 冻结 max 行 → 冷静期 → R3 提交时**两笔一并提交**，不引入第二种退款节奏

**数学自洽（pro ¥30 用 10 天升 max ¥60，随后立刻全退）**：
- 总付出 = 30 + 20 = ¥50 = 10 天 pro（¥10）+ 20 天 max（¥40）✓
- due = ¥40 → 腿A ¥20 + 腿B ¥20 → 净支出 ¥10 = 正好 10 天 pro 的钱 ✓
- 若按升级单差价单腿退（¥20）→ 净支出 ¥30，整个 pro 沉没，明显不公 ✗

### 6.3 边界与配套

- 冷静期：升级单已起算、不适用「未激活全额退」，按秒折算退（两腿）；页面明示（拍板项 4 定版）
- 剩余 < 24h：前端提示「快到期，建议到期后直接买 max」但不硬拦（拍板项 5，PM：同意——硬拦制造客诉，公式在短剩余下依然诚实）
- pay_fen < 1 分理论不可能（高档秒价差 × 秒数），四舍五入兜底 min 1 分
- 超窗（P2-3）：升级时刻两腿必在 1 年窗内（rem_sec>0 ⇒ 原单 age<周期≤365 天）；但包年 pro 升级后很久才退，PRO 腿可能超窗——**客服 runbook 登记此场景**（现有「超窗联系客服协商」条款兜底），不为此设计
- 退款页与订单详情（P1-6）：升级单退款预览/成功页展示两腿明细 + 「原 PRO 剩余价值已折入本笔退款、**不再恢复**」——refund.html 态七/态八已入原型；订单详情时间线复用快照加升级明细 kv

## 9. Non-goals（PM P2-5/P2-6/P2-1 折入）

- **landing 套餐区不同步**：面向匿名流量永远展示全价，与应用内个性化补差价并存不冲突
- **升级卡最多两个数字**：主价（补差）+ 续费辅助行；「MAX 剩余价值 ¥40」不上图（协议弹窗明细已有锚点），三数同卡必乱
- **降级**不立项（另议：排队 or 按秒退差价）
- **排队叠加升级 v1 不做**（已有排队更高档 → 隐藏升级入口）：顺序叠加（升级 max 剩余 20 天 → 排队 max 30 天）账目已验算可行，v1 从简；**重开条件**=出现明确的排队用户升级支持信号
