# 写作知识库 · 整体方案（C端 · 2026-10-30）

**一句话**：知识库分四层——L0 元模型（实体/关系/属性/约束/证据/视图/契约/版本，ontology 方法论）→ L1 实际概念（文风、文笔、世界、角色、手法、情节，各有自己的知识结构）→ L2 题材实例（仙侠·文风、都市·世界…）→ L3 派生库（按用途圈选）→ L4 消费（文风设定/世界设定/章级提示词/角色卡）。条目只有一份，库是视图，书是启用＋快照。第一个派生库（手法库）的详细设计见 `ai-novel-c端-手法库-设计说明.md`；技术选型见 `ai-novel-c端-写作知识库-选型.md`；本文件回答「整体怎么长」。

- 需求来源：飞书《写作知识库驱动正文生成系统 PRD》（docx `Es7EduR2ioNl5fx5TsWcVSPZn6b`，rev 12）＋用户 10-29 口头扩展（知识库派生出文笔库，后续世界设定库等）
- 原型：OpenDesign 项目 `Web Prototype` 里的 `knowledge-base.html`（v29，2026-10-30；六屏：知识库首页 / 派生库页 / 条目详情 / 派生新库 / 书内引用面 / 知识星图）；仓内镜像与截图见 `kb-captures/` 与本文 §14
- 关系：本文是**上位方案**；`ai-novel-c端-手法库-设计说明.md` 是其中「手法库」这个派生库的实现级细化（数据表名在本文统一为 `kb_*`，手法库文档里的 `technique_*` 是同构前身）

## 0. 先立四句话，后面都从这四句长出来

1. **先有元模型，再有概念，最后才是题材。** L0 是知识库自己的表示法（实体、关系、属性、约束、证据、视图、契约、版本）；L1 是实际概念（文风、文笔、世界、角色、手法、情节），每个概念有自己的知识结构；L2 才是按题材分区的实例（仙侠·文风、都市·世界）。**题材不是模型根，是实例的分区键。**
2. **知识条目只有一份。** 拆书拆出的「先果后因」不会因为进了手法库、又在某一章被用了一次，就多出副本；它只有一条，被库圈中、被书用过，都是引用。
3. **库不是分类，是用途。** L1 概念是「这是什么知识」；L3 派生库是「拿这批知识干什么」。「仙侠·文风库」＝在仙侠题材里圈一批文风实例，用来生成这本书的声音。同题材同概念可以派生出不同用途的库（冷硬派文风/古风文风）。
4. **书拿走的不是活引用。** 文风/文笔/世界是快照：启用时渲染进本书设定，此后书自己拥有，库再改不自动生效；手法是实时：逐章现挑；角色/情节是起草：挑原型、复制落卡（详见 §3）。

## 1. 目标与非目标

**本期目标（P0）**

- 一份账号级知识库：L0 元模型＋L1 六概念＋L2 题材实例；条目的增删改查、关系、来源与证据、按题材/概念/场面/来源检索。
- 派生机制（L3）：在某个题材里按某个概念圈实例 → 起名＋写用途＋选消费方式 → 成为一个库（库带题材＋概念）；库可被同题材的书启用。
- 三种消费契约跑通（L4）：**手法库**（逐章实时挑，落 user 提示词）、**文风库＋文笔库＋世界设定库**（快照进本书设定）、**角色设定库**（起草原型，落角色卡/角色库）。
- 书内可见：文风/世界设定面板显示「来自哪个库、几条、本书改过哪几条」；写作页右栏仍是「挑手法」入口；新建角色时可以从角色设定库挑原型。
- 拆书入库：拆书十维产物按题材与分类收进知识库，带来源与证据。

**非目标（本期不做）**

- 向量语义检索（P1；P0 用结构化筛选＋确定性排序，见选型文档）。
- 情节套路库的消费（P1；P0 只保留分类与派生位）；角色设定库的起草消费放到 P0-D，依赖角色库在途单。
- 多人协作、云端同步、移动端（产品既有边界）。
- 自动改写已启用库对旧书的设定（一律显式同步＋差异预览）。

## 2. 分层模型（自下而上）

> 上一版把「题材」画在最上面——那是**界面导航**，不是知识模型。正确的架构自下而上：最底层是知识库的元模型（ontology 方法论），上面是实际概念（文风/文笔/世界/角色/手法/情节），再上面才是按题材划分的实例。题材是上层的分区键，不是父类。

### 2.1 五层（四层模型＋应用层）

| 层 | 回答的问题 | 内容 | 谁维护 | 变化频率 |
|---|---|---|---|---|
| **L0 实现层 / 元模型** | 知识怎么表示、关联、溯源、派生、消费 | 实体、属性、关系、约束、证据、视图、契约、版本 | 开发者 | 极低 |
| **L1 概念层 / 实际概念** | 有哪些知识类型，各自由什么组成 | 文风、文笔、世界设定、角色设定、手法、情节（概念注册表） | 开发者 | 低 |
| **L2 题材层 / 实例** | 这个题材具体有哪些知识 | 仙侠·文风、仙侠·世界、都市·角色…… | 作家（拆书/手录/AI） | 高 |
| **L3 派生库 / 视图** | 这一批知识拿来干什么 | 仙侠·文风库、仙侠·手法库…… | 作家（圈选） | 中 |
| **L4 消费 / 应用** | 落到产品哪里 | 文风设定、世界设定、章级提示词、角色卡、剧情 | 代码（契约） | 低 |

```
L4 消费   ← 文风设定 / 世界设定 / 章级提示词 / 角色卡 / 剧情
   ▲ 启用/读取
L3 派生库 ← 题材＋概念＋用途＋契约（视图，不是新知识）
   ▲ 圈选
L2 题材层 ← 仙侠·文风 / 仙侠·世界 / 都市·角色 …（实例，genre 是分区键）
   ▲ 实例化
L1 概念层 ← 文风 / 文笔 / 世界设定 / 角色设定 / 手法 / 情节（概念注册表）
   ▲ 定义
L0 实现层 ← 实体 / 属性 / 关系 / 约束 / 证据 / 视图 / 契约 / 版本（元模型）
```

### 2.2 L0 实现层：知识库的元模型

这一层与「写小说」无关，回答「任何一条知识在系统里怎么表示」。八个原语：

| 原语 | 作用 | 落点 |
|---|---|---|
| 实体 Entity | 一条知识 | `kb_entries(id, user_id, genre, concept, title, payload_json, payload_version, evidence, status, rev)` |
| 属性 Property | 实体按概念 schema 携带的字段 | `payload_json`（Pydantic 按 concept 校验） |
| 关系 Relation | 实体与实体、实体与概念的关系 | `kb_relations(from_id, to_id, rel_type, note)`：`refines / contradicts / depends_on / instance_of / derived_from / applies_to` |
| 约束 Constraint | 必填、基数、值域、互斥 | Pydantic validator ＋ 库/消费前的检查 |
| 证据 Provenance | 来源、章号、引文、置信 | `evidence` 列（只读、不进提示词） |
| 视图 View | 从实例里圈一批（派生库） | `kb_libraries` ＋ `kb_library_items` |
| 契约 Contract | 视图怎么落到产品 | `live / snapshot / draft` ＋ 渲染器 |
| 版本 Version | 实体/库/书绑定的版本 | `rev`、`snapshot_json` |

方法论：**轻量 property graph ＋ 概念 schema 注册表**——不是 RDF/OWL（不需要推理机），不是 EAV（太散），不是每概念一张表（迁移爆炸）。选型见 `...-写作知识库-选型.md` §3。

### 2.3 L1 概念层：六个实际概念

这一层是「实际概念」。每个概念有自己的属性 schema、关系、质量规则、消费契约。**概念是开发者维护的注册表，作家不定义概念，只填实例。**

| 概念 | 它是什么 | 属性 schema（示例） | 与其他概念的关系 | 消费契约 |
|---|---|---|---|---|
| 文风 | 这本书的声音 | 叙事身份 role、基调 tone、视角 pov、语言口径 register、示范段 samples | 文笔 implements 文风；世界/角色为文风提供语料 | snapshot → `style.role/style_samples/few_shot` |
| 文笔 | 句子层面的写法 | 句式 syntax、节奏 rhythm、描写 description、对白 dialogue、修辞 rhetoric、禁用词/句式 banned/tic | implements 文风；手法可调用句法 | snapshot → `style.rules/craft/banned/tic` |
| 世界设定 | 舞台与规则 | 舞台 stage、力量 power、代价 cost、势力 factions、历史 history、细节 extra、铁律 constraints | 角色设定 belongs_to 势力；手法 depends_on 铁律 | snapshot → `world` KV |
| 角色设定 | 人物的造法 | 档案八格、关系位置、语言特征、弧光 | belongs_to 世界设定/势力；手法 depends_on 角色状态 | draft → 角色卡/角色库 |
| 手法 | 场景打法 | 触发 when、指令 instruction、反面 negative、场面 scene、情绪 emotion | depends_on 世界设定/角色设定；applies_to 文笔 | live → 章级 user 提示词 |
| 情节 | 结构套路 | 步骤 steps、爽点/钩子、卷位、节奏 | uses 手法；drives 角色弧光 | draft → 剧情抽卡/推演（P1） |

**概念解读三件套**（10-31 并入）：每个概念/子概念标配 `definition`（子概念也必填）＋`aliases`（同义词，拆书映射/搜索归一）＋`interp_json{positive_ref,negative_ref}`（标准正例/反例各指一条条目）；关系层带元数据（六类的定义域/值域/逆关系/函数性，见数据结构文档 §10）。**概念注册表**（`kb/concepts.py`）：`CONCEPTS = {name: {schema, relations, quality_rules, renderer, contract}}`。新增一个概念＝注册一条＋写渲染器，不改表结构、不改迁移、不改备份段。

**概念不是平的，是树**：全部题材 → 题材（21 类目录）→ 概念（六类）→ 子概念（题材下的细分）→ 条目。示例（仙侠/修真）：

```
仙侠/修真
├─ 文风 → 冷峻克制
├─ 文笔 → 句式 / 对白 / 禁用
├─ 世界设定 → 力量 / 势力 / 铁律 / 历史 / 舞台
├─ 角色设定 → 主角原型 / 反派原型
├─ 手法 → 打斗 / 文戏 / 开篇
└─ 情节 → 擂台扬名 / 断物立誓
```

- 概念（L1）是稳定的类，有 schema/属性/契约；子概念（L2）是题材下的细分，随题材长。
- 条目挂在子概念（叶子）下；概念关系（实现/依赖/落笔/调用）走概念节点，不走条目。
- 概念树是本体视图的骨架；星图按这棵树排层级。
- **题材目录不是一个根，是 21 个根**：题材词表是前后端同源的封闭目录（前端 `client/frontend/src/lib/themeCatalog.ts`，后端 `genres/theme_catalog.py`，parity 测试守着），当前 21 类。星图画「全部题材（黑洞）→ 21 个题材」；每个题材都是自己那棵概念树的根，**没建树的题材也画出来（空枝）**，不做成「只有仙侠/修真」。
- P0 概念/子概念由种子维护，作家只填条目；P1 允许作家在题材下加子概念。

### 2.4 L2 题材层：实例分区

- `genre` 是**概念树的根**，也是实例的分区键。题材目录是封闭 21 类（前后端同源）；每个题材都有一棵（可以为空的）概念树，六类概念是全局类，子概念是题材实例层。
- **21 个题材全部进星图**：已建树的题材标名字＋条目数，未建树的题材是空枝（一个点，悬停出题材名），可以点进去看空态；题材不是「有数据才出现」。
- **题材根不进 `kb_concepts`**：21 类根直接复用题材目录，`kb_concepts.genre` 只存题材 key；概念/子概念行按需懒建。这样题材词表只有一份，不会两边漂移。
- 一个条目一个主题材＋少量题材标签；跨题材（都市异能/仙侠都市）用主题材＋标签，不拆成两条。
- 题材目录复用既有 `themeCatalog.ts` / `theme_catalog.py` 的 21 类（每类自带 subTypes 子题材，P0 不把子题材放进本体树）；P0 是封闭目录，不允许作家自造题材。
- `genre=""` 表示**通用知识**（如「短句压节奏」「打斗场面文风」），**P0 就要有**（10-31 拍板）：通用文风/文笔是每本书的兜底基线，也是跨题材复用的场面写法来源。

**为什么六类概念不能被题材复制**：如果题材是类的父类，会出现「仙侠文风」「都市文风」两套 schema——同一概念的属性和消费都要重写。现在题材只做两件事：当概念树的根、当实例的分区键；六类概念保持一份，子概念按题材长。

### 2.5 L3 派生库：视图，不是知识层

- 派生库 ＝「在某个题材里，按某个概念圈一批实例，给它一个用途和契约」。
- 库不复制条目；`kb_library_items` 是 join。
- 同题材同概念可以多个库（冷硬派文风/古风文风）。
- 库是用途层，不产生新知识；删库不影响条目。
- **星图是另一个视图**：概念树（概念/子概念）＋条目实例＋关系（L0）画成本体星图，不经过库；库回答「拿它干什么」，星图回答「它和谁有关系、属于哪个概念」。

### 2.6 L4 消费：落到产品

| 概念 | 落点 | 方式 | 现有代码/新增 |
|---|---|---|---|
| 文风＋文笔 | 基线→`style` KV；场景条目→章级 user 块 | **混合**（基线快照＋场面逐章挑） | `settings/style_model.py`＋`settings/render.py`＋`build_scene_style_block()` |
| 世界设定 | `world` KV | 快照 | `prompt/context.py`＋`settings/world_model.py` |
| 角色设定 | 角色卡/角色库 | 起草（复制落卡） | 角色库在途单＋`render_character_prototype()` |
| 手法 | user 提示词 | 实时 | `build_technique_block()` |
| 场面文风/文笔（带 `when_json` 的条目） | user 提示词（与手法同块） | 实时 | 与手法共用选择器 |
| 情节 | 剧情抽卡/推演 | 起草 | P1 |

反馈回流：手法逐章「有用/没用」；文风/世界按同步差异「采纳/本书改过保留」；角色按「用了哪个原型/改了哪些格」。

### 2.7 界面与架构是反的（重要）

- **架构自下而上**：L0 元模型 → L1 概念 → L2 实例 → L3 库 → L4 消费。
- **界面自上而下**：题材（L2）→ 概念（L1）→ 条目（L2 实例）→ 库（L3）→ 消费（L4）。
- 界面把题材放第一，是因为作家的第一直觉是「我写的是什么题材」；但它只是 L2 的筛选器，不是模型根。**别把导航当架构。**

## 3. 三种消费方式（整套方案的分水岭）

这是本文最重要的设计判断：**不是所有库都该「实时挑」**。

| | 实时型（手法库） | **混合型（文风库 / 文笔库）** | 快照型（世界设定库） |
|---|---|---|
| 消费时机 | 每章生成前 | 启用库 / 手动同步时 |
| 落点 | user 提示词末尾一节，不落库 | **基线条目**→本书 `style` KV（system 恒定层）；**场景条目**（带 `when_json`）→逐章进 user 块 | 本书 `world` KV，system 恒定层 |
| 库改动后 | 下一章自动生效（因为每次现挑） | **不自动生效**；显示「库有 2 条更新」，作家点同步才落 |
| 书内改写 | 只改本章清单，不回写库 | 改本书设定（覆盖），标「本书改过」，不回写库 |
| 为什么 | 章级差异必须逐章变，快照会让每章一样 | **书的基线声音恒定（spec），场面的写法差异逐章挑**：基线给身份，场景给当章的句法/节奏/描写偏移 | 世界是事实，事实不随场面变；且必须逐章字节一致（spec），作家逐句改 |
| 风险 | 同批手法轮播 → 新鲜度扣分 | 库更新不同步 → 过期提示＋一键看差异 |

第三种（起草型：角色设定库）见 §3.2；上面这张表只对比「写正文」的两种。

**文档里的措辞也要分开**：手法库叫「挑／这次用不用」；文风库/文笔库/世界设定库叫「启用／同步／本书改过」；角色设定库叫「挑原型／复制落卡」。不要用同一套动词，否则作家会以为文笔库也是每章变。

### 3.0 题材是库的作用域

- **库带题材＋概念**：`kb_libraries.genre` 与 `.concept` 决定这个库属于哪个题材柜的哪一格；「仙侠·文风库」只服务仙侠书，「都市·文风库」只服务都市书。
- **书只启用本题材的库**：一本书有且只有一个主题材；跨题材的书（如「都市异能」）先选一个主题材，另一个作为题材标签参与匹配，不跨柜启用。
- **同题材同分类互斥**：一本书同一题材同一分类只能启用一个库（不能同时用「冷硬派文笔」和「古风文笔」两套声音）；换库＝换源，走一次同步差异预览。

### 3.0 启用规则

- **同题材同概念互斥**：一本书同一题材同一概念只能启用一个库；换库＝换源，走一次同步差异预览。
- **启用即记版本**：写 `kb_book_bindings(novel_id, library_id, rev, snapshot_json, synced_at)`；之后库变了，书不会变，只在来源行提示「库有 N 条更新」。
- **删库/删条目不惊动已启用的书**：快照型消费的书内设定已经是一份独立文本，库或条目被归档后书照常写；来源行显示「来源库已移除」，可一键解除绑定。
- **多书独立**：同一库被多本书启用，各书快照、覆盖、同步互不影响；库页的「N 本书在用」只是计数。

### 3.1 快照怎么落（不新造渲染层）

- **文风库** → `style.role / style_samples / few_shot_examples`（叙事身份、示范段、短句示例）；**文笔库** → `style.rules / craft / banned_words / tic_patterns`（硬约束、描写手法、禁用词、禁用句式）。两库都走 `settings/style_model.py` 的 7 个白名单键，条目按自己的 `slot` 落键。
- 世界设定库 → 走现有 `world` KV 的 8 个键（`stage/power/cost/history/factions/constraints/extra` 七个内容分区＋`no_power` 开关）；条目按 `section` 归位，冲突条目在同步预览里并排显示。
- 两条路复用现有的「拆书→建书」应用函数族（`deconstruct/settings_map.py`、`deconstruct/apply.py` 的映射与去重逻辑），只是输入从「拆书产物」换成「库成员渲染结果」。这样不新增一套设定写入协议。
- 同步预览必须显示三件事：新增几条、更新几条、本书改过而被保留几条。默认只加不改（保护作家手改）。

### 3.1b 混合型怎么落（文风/文笔，10-31 拍板）

**一条文风/文笔知识看它带不带适用条件：**

- **不带 `when_json` ＝ 基线条目**：这本书的声音底座（叙事身份、总体句法、总禁用）。启用库时快照进 `style` KV（走既有同步），此后逐章字节一致，作家逐句改。
- **带 `when_json`（scene/emotion/chapter_pos）＝ 场景条目**：这个场面才用的写法（“打斗：句长压到 12 字内，动词连用”“哭戏：禁止比喻，只写动作”）。**不进快照**，写章时和手法一起按剧情挑，进 user 动态块。

**场景条目的槽位限制**：文风只许 `tone/register/sample`（**不许 `role/pov`**——叙事身份和视角是书级恒定，场面不许改）；文笔四槽全开（rule/craft/banned_word/tic 全是列表，叠加）。合并规则：**基线在前、场景在后追加**，列表槽拼接去重；`role/pov` 只来自基线。

**三级知识与优先级**（同槽多条时）：`题材+场景`（仙侠·打斗文风）＞ `通用+场景`（打斗文风）＞ `题材基线`（仙侠文风）＞ `通用基线`。分数并列时看有用率与新鲜度（同手法打分）。

**selector 复用**：场景文风/文笔与手法走同一个匹配器（`when_json` 命中∪实体命中），只是配额分开——手法 ≤6 条、场面写法 ≤4 条，动态块总预算 ≤2K tokens。

### 3.2 起草型（角色设定库）

角色设定不进正文提示词，它是**新建角色时的原型供给**：

- 消费时机：新建角色 / 往角色库里收角色时；不是每章生成时。
- 落点：角色卡草稿（档案八格、说话方式、外貌/年龄/性别），作家改名改设定后复制落卡。
- 库改动后：下次起草用最新；已经落卡的角色不回写、不联动。
- 为什么不做快照进书：角色卡是书内资产，一个书里的角色会随剧情改；库里的原型只是起点，复制落卡后书自己拥有。
- 与角色库（在途单）的边界：角色库是「角色成品」的跨书池；角色设定库是「角色原型/写法」的跨书池。前者收角色，后者收角色的造法；同一条原型可以被多个角色复用。

### 4.6 AI 定期整理（关系形成）

- **谁形成关系**：AI，不是作家。作家不拖节点、不连边；只查看星图和反馈「这条关系不对」。
- **触发**：拆书入库后自动一次；应用启动时若距上次 >7 天自动一次；作家点「现在整理」立即一次。一次只整理一个题材，避免大调用；**没有条目的题材跳过（空枝不跑）**。
- **输入**：本题材的条目（标题/指令/证据）、概念树（概念/子概念）、现有关系（避免重复）。
- **输出**：关系提案 `{from,to,type,confidence,note,evidence}`，类型限定 `implements/depends_on/applies_to/uses/refines/related_to`。
- **校验**：端点存在、类型在白名单、无自环/重复、confidence 0–1；≥0.75 直接 active，0.5–0.75 进 pending（不上星图），<0.5 丢弃；旧关系被新关系覆盖时 `superseded`。
- **写入**：`kb_relations(source='ai', confidence, status, run_id, evidence)`；`kb_organize_runs` 记本次范围、模型、扫描条数、新增/更新/跳过、耗时、错误。
- **星图**：只读 `status=active`；星图顶部显示「AI 整理 · 每周一次 · 上次 10-28 02:14 · 新增 4 · 更新 2」，题材树里关系面板显示「AI 整理 · 置信 0.92 · 10-28」；「这条不对」写反馈，下次整理重新评估。
- **模板**：提示词仓新增 `kb_organize`（PRO）；不在客户端写死提示词；随提示词包发布。
- **成本/门禁**：PRO；按概念分批、每次条目上限 N；失败不阻断知识库，只记 run。
- **与拆书的关系**：拆书是条目供给源，AI 整理是关系供给源；两者都不产生原文语料。

## 5. 数据模型

账号级（不挂 `novel_id`，不随书级联；照角色库 `character_library` 先例）：

| 表 | 关键字段 | 说明 |
|---|---|---|
| `kb_concepts` | id、user_id、**genre**、parent_id、name、level（1=六类概念/2=子概念）、definition、properties_json、sort、status | 概念/子概念树；**题材根不复制进本表**，直接复用 21 类题材目录；P0 只读种子，P1 可增子概念 |
| `kb_entries` | id、user_id、**genre**（主题材）、**concept**（L1 六类之一）、**concept_id**（叶子子概念）、title、payload_json、payload_version、instruction、negative_example、when_json、evidence、status、rev、src_kind/src_ref/src_key/src_novel_name、created_at/updated_at | 实体；`payload_json` 按 concept 强校验；`concept_id` 指叶子；`src_key` 幂等；索引 `(user_id, genre, concept, concept_id, status)` |
| `kb_entry_tags` | entry_id、dim、value | 多维标签索引（concept/genre/scene/emotion/slot/tag）；写入时同事务重建，过滤/计数/派生规则走它 |
| `kb_relations` | from_id、to_id、rel_type、strength?、note、source、confidence、status、run_id、evidence、updated_at | 端点可以是概念（`concept:*`）或条目（`entry:*`）；`source=ai/seed`；`status=active/pending/superseded/rejected`；唯一 `(from_id,to_id,rel_type,status=active)` 语义；**星图只读 active** |
| `kb_organize_runs` | id、user_id、genre、status、model、api_config_id、entries_scanned、relations_added、relations_updated、relations_skipped、started_at、finished_at、error | AI 整理流水；一次一个题材；失败只记 run，不阻断知识库 |

| `kb_library_items` | library_id、entry_id、sort、added_at | 圈选 join；唯一 `(library_id, entry_id)` |
| `kb_prefs` | novel_id、entry_id、weight、adopt_count、drop_count、last_used_at | 仅手法实时消费用；文笔/世界不用 |

| `kb_match_items` | run_id、entry_id、clause、decision、score、reason_json、used、helpful | 逐条清单与反馈 |

**题材根为什么不进 `kb_concepts`**：题材目录是前后端共用的封闭词表（21 类，parity 测试守着），复制一份必然漂移；`kb_concepts.genre` 只存题材 key，概念/子概念行按需懒建。空题材没有行＝空枝，星图仍从目录画出来。`kb_organize_runs.genre` 也存同一个 key。

**关系表为什么在 L0**：概念之间的关系（文笔 implements 文风、角色 belongs_to 势力、手法 depends_on 铁律）是 ontology 的一部分；P0 可以先只写不查，但表要留，否则以后加关系要动迁移。

**标签索引为什么单独一张表**：题材/概念/场面是热过滤与派生规则的输入，放 JSON 列只能全表扫；tag 表可加索引、可计数（题材/概念计数都走它）。payload 仍是完整事实源，tag 表是它的物化索引，坏了可重建。

**为什么 `kb_book_bindings` 在书内**：它决定「这本书用了哪个库的哪一版」，必须跟书一起备份/恢复；库内容本身是账号级，走配置包。恢复单书时即使库不在，书内设定快照仍然完整（因为快照型已落 `style`/`world`），只是显示「来源库不在本机」。

**每类知识的 payload schema**：六概念的 `payload_json` 字段表（字段名＝消费端真实键：文风→`STYLE_WRITE_KEYS`、文笔→`rules/craft/banned_words/tic_patterns`、世界→`V2_KEYS` 8 键、角色→角色卡 `dossier/cog` 格、手法→`instruction/negative/scene/emotion/steps`＋`when_json`）、渲染映射、校验闸门与完整示例，见 **`ai-novel-c端-写作知识库-数据结构.md`**（一条知识＝公共信封＋按概念强校验的 payload；一条只讲一个 slot）。

**手法库的旧表名**：`technique_entries/runs/items/prefs` 在实现时统一改名 `kb_*`，字段增加 `genre`、`concept='手法'` 与 `payload_json`（指令/反面/场面/情绪进 payload，通用检索列仍保留）。迁移策略见 §9。

## 7. 生成链路里的位置（一次写章的全景）

```
设定页                        写章时
├─ 文风库＋文笔库（快照）──→ style KV ──┐
├─ 世界设定库（快照）──→ world KV ──────┤
└─ 手法库（实时）──→ 每章匹配 ──┤
                                ├─ system：铁律/文风/世界/卷纲/人物锚（逐章一致）
                                └─ user：章级素材＋本章手法（收尾行前）
```

- **system 不动**：文风/世界是书级恒定，继续吃前缀缓存；写法是章级差异，进 user；角色设定不进正文。
- **零提示词包改动**：写正文的四条链都在代码里（文风/文笔/世界已有，手法新增在 user 尾部）；角色不走提示词，落角色卡。P0 不需要发提示词包。
- **可关闭**：书没有启用任何库 → 一切照今天；这是每本书的退化路径。

### 7.1 提示词组装流水线（终态 · 用户拍板 10-31）

**知识库的最终消费者就是写正文的大模型：写章时根据剧情判断需要哪些知识，组装进提示词，整包丢给大模型。** 组装分两层，判断只发生在动态层：

```
写章请求（章纲/剧情）
   ↓
① 稳定层（system，本书恒定，不参与逐章判断）
   书内设定快照＝文风(role/示范段)＋文笔(rules/craft/禁用)＋世界(8键/铁律)
   ← 启用库时一次性落入，之后书自己拥有（spec：system 逐章字节一致）
   ↓
② 动态层（user 末尾、收尾行之前）——「根据剧情判断」只作用在这里
   剧情解析：章纲 → {scene, emotion, chapter_pos, 卷位, 本章实体(角色/地点/道具)}
   ↓ 选择器（一个匹配器，两类知识）
   候选＝手法条目 ＋ **场景文风/文笔条目**（带 when_json 的文风/文笔，10-31 起）
   P0 规则匹配器（确定性、免费、可测）：
     when_json 命中（scene/emotion/chapter_pos）∪ 实体命中（depends_on 的铁律/角色在本章出现）
     优先级：题材+场景 ＞ 通用+场景（通用=genre=""，P0）
     打分＝匹配度 × 有用率(kb_prefs) × 新鲜度(近 N 章未用过)
     配额：手法 ≤6 条、场面写法 ≤4 条；动态块总预算 ≤2K tokens（每条 instruction ≤240 字）
   合并：场面写法**追加在书的基线之后**（列表槽拼接去重；role/pov 只来自基线，场景条目禁改）
   P1 LLM 选择器（PRO，可选增强，不替规则）：
     输入＝章纲摘要＋候选条目{title, instruction 摘要, when}；输出＝选中 id＋理由
     落 kb_match_runs.brief_json；结果仍过预算闸与白名单，超规降级回规则匹配
   ↓
③ 组装（唯一进动态层的文本是条目 instruction/negative）
   user ＝ [作家可编辑的写章输入] ＋ [前文衔接/上下文] ＋ [本章写法块＝场面文风/文笔＋手法] ＋ WRITE_CLOSING_LINE
   ↓
④ 全链留痕：每次生成落 kb_match_runs ＋ kb_match_items{clause, decision, score, reason}
   写完逐条「有用/没用」→ 回写权重 → 下次打分。这是“根据剧情判断”的学习闭环。
```

**选择器工程补丁（prompt-engineer 评估 · 10-31，并入流水线）**：

1. **信号来源＝作家章纲（10-31 定）**：剧情本来就是作家在章纲里定义的，选择器**只读章纲，不自己发明剧情判断**。章纲现有字段直接映射（`write/prompt_sources.py` 同源）：
   | 选择器信号 | 章纲来源 | 方式 |
   |---|---|---|
   | 本章实体（角色） | `outline.characters`（出场角色）＋ `chapter_characters` | 直取 |
   | scene/emotion/chapter_pos | `outline.summary`（章纲概要）＋ 剧情条目 `plot_items` | **封闭词表＋别名归类**（打斗{交手/出招/追逃}、文戏{对话/日常/感情}、开篇/转折/收尾；注册进 `kb/concepts.py`）——确定性规则，不跑模型 |
   | 卷位 | 卷纲/章节序号 | 直取 |
   归类不出的章（作家没写场面线索）→ 只出基线快照＋通用场景兜底，**不硬猜**；P1 可在章纲表单加两个可选下拉（场面/情绪基调）让作家显式声明，仍是作家定义。
2. **多场面章**：P0 按**主导场面**选（章纲里占比最高的场面，最多再带 1 个次要场面，配额减半）；逐段感知 P2。
3. **同槽冲突**：`rule/craft/tic` 同槽基线与场景**同时命中时场景覆盖基线**（“≤22字”遇上“≤12字”只留场景那条），`sample/banned` 追加不去重冲突——由组装器做，选择器只管挑。
4. **重试确定性**：同一 `chapter_id + brief_hash` 重试**复用上一次 `kb_match_run`**（新鲜度只在首次计算），重试提示词字节一致。
5. **块格式与防注入**：写法块固定模板（见下）；条目文本入库时剥掉能伪装成结构标记的字符（块界符、收尾行原文、行首 `#`/`---`）；块内条目一律条件标签＋短句，不给模型“执行任意指令”的语义位。
6. **评估闭环**：golden 集（每题材 20 章：章纲＋人工标注应选条目）回归选择器；线上指标＝有用率、场景覆盖（有 ≥1 条命中的章占比）、冲突率（同槽双写次数，应为 0）。

**写法块模板（user 层，收尾行前，≤2K tokens）**：
```
【本章写法指引】以下只约束写法，不改变剧情；标注“本场”的规则优先于全书基线。
- [本场|打斗|句式] 打斗段落一句不超过 12 字，连续动词不超过两个
- [本场|打斗|禁用] 不要三个以上连续动作塞进一句
- [基线|禁用词] 仿佛（改成直接比喻或删掉）
- [手法|打斗] 先给果再补因：第一句直接写结果，第二句起补动作
```

**四条红线不变**：原文/证据/示范段之外的拆书原文永不进提示词；system 逐章字节一致（剧情判断不碰稳定层；场面文风/文笔只进 user）；写法块（手法＋场面文风/文笔）不落任何书内设定（下一章重新挑）；角色设定不走提示词（落角色卡）。世界设定保持纯快照：**事实不随场面变**，P1 可加“本章相关设定强调”（按实体命中挑 1–2 条世界条目进 user），但仍是事实的引用不是改写。

**为什么 P0 用规则不用大模型挑**：正文链对提示词确定性敏感（同一章重试不该变知识）、零成本零延迟、决策可解释可测试；“智能判断”作为 P1 增强叠加在规则之上（LLM 只在候选>预算时做裁剪），而不是替代。

## 8. 导入与证据

### 8.1 拆书十维 → 条目类型

| 拆书维度 | 去处 | 说明 |
|---|---|---|
| `techniques` / `avoid` / `borrowable` | 手法条目 | 现有映射 `deconstruct/settings_map.py:479-524` |
| `style` | 文风条目（role/示范/短句）＋文笔条目（rules/craft/禁用） | 现有 `style_body` 映射后按 slot 拆两类 |
| `world` | 世界设定条目（按分区） | 现有 `world` 映射 |
| `characters` | 角色条目（P0-D，起草型） | 档案八格→角色原型；角色库另有成品入口 |
| `mainplot` / `structure` | 情节（P1） | 暂不入库 |

**题材从哪来**：取拆书任务的 `genre` 产物（源书的题材）；取不到时归入「未定题材」，导入清单里让作家选一次，不硬猜。一个条目只有一个主题材；跨题材的写法用题材标签补充（如「仙侠」条目可带「修真」标签）。

导入是**任务的显式动作**（拆书完成页「收进知识库」），幂等键 `(user_id, src_ref, src_key)`；重复导入跳过已收，不静默更新。导入闸：
- **长度闸**：指令压到 240 字，句末断；断不出整条不收。
- **原文闸**：与拆书原文比对，连续 ≥20 字逐字相同 → 标「像原文摘录，改成自己的话」，默认不勾。
- **证据**：章号＋原文摘录进 `evidence`，只读展示，永不进提示词。

### 8.4 数据来源（不只拆书）

| 来源 | 通道 | 去向 | 证据 | 档位 |
|---|---|---|---|---|
| **拆书**（主供给） | 拆书完成页「收进知识库」显式动作，幂等键防重 | 手法/文风/文笔/世界/角色 五类 | 章号＋原文摘录（只读，不进提示词） | AI 拆书 PRO |
| **手录** | 知识库首页空态 CTA「记第一条」→ 选题材/概念 → 表单 | 任意概念 | 无证据字段，`src_kind='manual'` | 免费 |
| **既有链路沉淀** | 文风蒸馏 step4 确认卡加「存进知识库」；拆书产物建书时同一份产物同时入库（一份产物两用） | 文风/文笔（蒸馏）、五类（建书） | 蒸馏：来源书；建书：同拆书 | 免费/随原功能 |
| **种子** | 装包即有：21 题材目录＋六概念 schema＋子概念树（`kb_concepts` 只读） | 结构层，不是条目 | — | 免费 |
| ~~AI 整理~~ | 只读条目补 `kb_relations`，**永不写条目** | 关系层 | 关系带证据引用 | PRO |

可选（待拍板）：首发带官方种子条目（每题材 3–5 条拆书精华），让新账号打开不是全空——运营决策。

### 8.5 初始化（冷启动）

初始化分三层，只有第二层需要用户动作：

1. **结构层（装 App 即有，零数据）**：21 题材目录、六概念 schema、子概念树、空态文案。首次打开知识库＝21 个题材全在（空枝）、六概念页签可用、0 条目；每个题材显示空态卡「先拆书或手录，条目到位后这里会长出五类库」。**库不预建**——库是视图，没有条目就没有库。
2. **条目层（首次动作，按门槛排序）**：
   - **手录一条**（免费、30 秒）：空态 CTA → 选题材/概念 → 一条指令＋可选示范段；
   - **文风蒸馏沉淀**（已有功能复用）：确认卡勾「存进知识库」；
   - **导入自有书 → AI 拆书 → 收进知识库**（PRO，一次喂厚一个题材）：一次拆书 ≈ 该题材长出几十条带证据的条目。
3. **库层（自动，不需要作家「派生」）**：某题材某概念**首次有条目入库时，系统自动生成该题材×概念的默认库**（自动圈＝该题材该概念的全部条目，名字＝「文风库/文笔库/…」，作家可在库页改名/停用；手动圈选 P1 再议）。这对应 10-30 拍板「每个题材各有一套子库」：库随条目自动长，不是初始化时手工建。
4. **关系层（后置自动）**：首次入库后 AI 整理自动跑一次（拆书入库触发），补概念关系；之前星图只显示层级。

**题材成长循环**：空题材 → 拆一本书 → 条目入库 → 该题材五类默认库自动成型 → 书内可启用 → 空枝变实枝。

**度量**：首条目时间（目标 <3 分钟，手录路径）；首题材成型（≥3 个概念有条目）；首库被书启用。

### 8.2 文风/文笔条目的特殊形状

文风/文笔不是一句指令能说清的。一条文风条目可以是「一个声音侧面」：身份、一条硬约束、一条描写手法、一段示范、一组禁用词。渲染时按 `slot` 落到 style 的对应键；同一 slot 多条 → 同步预览里并排，作家选一条或都保留（`rules`/`craft` 是列表，可以都保留；`role` 是单值，必须选一条）。

### 8.3 世界/角色条目的特殊形状

一条世界设定条目属于一个分区（舞台/力量/代价/势力/历史/细节/铁律）。同一分区多条 → 都保留，按 sort 拼接；`constraints`（世界铁律）逐条渲染，不合并成一段。一条角色条目是一条「造法」：档案八格＋说话方式＋关系位置，复制进角色卡时逐格映射，不写正文。

## 10. 质量、反馈与门禁

- **覆盖度**：文风库/文笔库启用后，文风设定的 7 个槽有几个来自库（文风：身份/示范/短句；文笔：约束/描写/禁用词/禁用句式）；世界设定库 7 个内容分区有几个有条目；角色设定库的 8 个档案格有几个来自原型。库页显示「这本书还缺：示范段、禁用词」。
- **冲突**：同一槽多条（尤其 `role` 单值）在同步预览里标冲突，必须选一条；不静默覆盖。
- **过期**：库成员/条目改动后，启用本书显示「库有 2 条更新」；不自动同步。
- **反馈**：手法库逐章「有用/没用」；文风/文笔/世界库的反馈＝同步时「采纳/本书改过保留」的计数，不做逐句打分（无法归因）；角色设定库的反馈＝「用了这个原型/改了哪些格」。
- **门禁**：知识库浏览与管理免费（不烧 AI）；手法实时消费随「生成正文」走 PRO；文风/文笔/世界快照落设定免费；角色设定库的「挑原型」随角色库/角色创建能力；AI 起草/拆书入库随各自能力既有门禁。

## 12. 风险

| 风险 | 应对 |
|---|---|
| 概念越加越多，首页变成表单集 | 只允许「有消费链」的概念进 P0；新概念必须同时定义 schema、关系、渲染契约、验收 |
| 派生库与概念混淆 | UI 上概念是 pill，库是卡片；库页永远写「题材·概念＋用途」；文档与界面都区分「挑」「启用」「挑原型」 |
| 快照后库更新，书悄悄变 | 不自动同步；差异预览默认只加不改；本书改过的一律保留 |
| 文笔条目颗粒度失控（一条一整套文风 vs 一条一个侧面） | 一条一个侧面（一个 slot），同一 slot 多条在同步时选；库页显示槽位覆盖 |
| 拆书产物直接入库带原文 | 导入原文闸＋证据只读；示范段仍走 style_samples 通道与 6×500 上限 |
| 与角色库/手法库撞备份版本 | 三单同批一个升版号（§9） |
| 手法库设计被本文改名后文档漂移 | 手法库文档顶部加「本文是整体方案的手法库细化，表名以 kb_* 为准」的注记（已加） |
| 题材越分越细，最后变成几十个柜 | 题材目录复用既有 21 类词表（封闭），P0 不允许自造题材；一个条目一个主题材＋少量题材标签；「未定题材」允许存在 |
| 文风/文笔拆得太细，作家分不清 | 概念层拆两个，界面页签也拆两个；用一句话说明差别——文风是「这本书的声音」，文笔是「句子怎么写」；导入时按 slot 自动归位 |
| 关系表建了但没人用 | P0 由 AI 整理写入、星图只读展示；不靠人手填 |
| AI 整理出幻觉关系 | 置信度阈值＋证据字段＋低置信 pending 不上屏＋「这条不对」反馈；关系不写进正文提示词 |
| AI 整理成本 | 一次一个题材、按概念分批、每次条目上限；每周一次＋拆书后触发＋手动触发；PRO 门禁 |
| 角色设定库与角色库边界 | 角色库收「角色成品」，角色设定库收「角色的造法」；前者复制落卡，后者只出原型；两边不互相回写 |

## 13. 待拍板

1. **概念拆分**：文风与文笔拆成两个概念、两个库（本文建议，因为 `style` KV 天然分 role/samples 与 rules/craft/banned/tic）还是合成一个「文风文笔」概念？
2. **关系深度**：P0 只建 `kb_relations` 表、写少量关系（belongs_to/depends_on），还是同时做关系可视化/推理？本文建议 P0 只写不查。
3. **通用知识**：`genre=""` 的通用条目不进题材柜（P1），还是 P0 就允许「通用」柜？
4. **题材粒度**：一个条目一个主题材（本文建议）还是允许多题材？跨题材（都市异能/仙侠都市）怎么归档——主题材＋题材标签，还是允许条目同时进两个柜？
5. **P0 分几批**：P0-A 只做底座＋手法库，文风/文笔/世界放 P0-B；还是同批？本文建议分批，因为「快照＋同步差异」是第二套交互。
6. **世界设定库的启用语义**：启用即覆盖本书现有世界设定，还是只「并入缺失分区」？本文建议默认并入＋冲突并排选。
7. **库的粒度**：同一题材同一概念一个库，还是允许多库（冷硬派文风/古风文风）？本文建议允许，P0 先只建一个默认库。
8. **角色设定库的落点**：只喂「新建角色」表单，还是同时喂角色库的收录面板？依赖角色库在途单的最终形态。
9. **派生是否支持「按条件自动圈」**：P0 手动勾选，还是同时做题材/来源规则？本文建议 P0 手动，规则留 P1。
10. **书内入口**：设定页文风/世界面板顶部加来源行（本文建议），还是知识库只在全局工具里、书内不露出？
11. **全局入口**：知识库挂「写作工具 ▾」（与角色库同槽，本文建议），还是顶栏一级导航？
12. ~~界面用词「派生」~~ **已拍板（10-30）：UI 去掉「派生」**——流程与入口整体移除；架构层 L3 概念与 `kb_libraries` 保留；新建库入口 P1 再议。
