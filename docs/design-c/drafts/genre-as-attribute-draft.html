题材即属性：建书即选，面板退役v2

awesome-novel 给出的真正启示不是「收纳」，而是题材从头到尾就不该是作家要处理的表单——它是建书时的一个选择，和之后 AI 自动遵守的知识。

核心想法（三条）
① 选题材发生在建书那一刻（= awesome-novel init --genre 的时点）：建书弹窗的粗分类下拉升级为 24 题材选择器，书建好题材即定，AI 从第一章按规则写。
② 设定流里没有「题材面板」：题材从 8 项设定任务中退役（8→7），降为设定视图顶部一张属性卡——不计进度、不需确认、没有「第一步」。
③ 规则编辑 UI 整体下架：19 行编辑器与注入开关从作家界面消失，27 条预置规则在只读弹层中透明呈现；API / payload 原样保留继续下发，未来真有精调需求再做「规则包」，不做表单。
口径前提
  • 后端 DB 已 seed 24 预置题材（含全部档案字段）；本稿不动 DB schema、不动 payload 字段语义。建书后前端静默 PUT settings/genre 一次，与今天手动选题材的落库产物逐字节一致。
  • 样例数据取 awesome-novel xianxia.md 真实档案：禁忌 8 + 爽点 5 + 章节类型 5 + 节奏 3 + 少用词 6 = 27 条。
  • 故事骨架（selected_arc_id）本期随属性卡弹层单点读写 genre 记录；终局归属「主线」面板，待后端迁移后归位，本期不动。

    推荐 v2 整稿落地。工程切片：① 建书弹窗选择器 + 建书后静默初始化 genre settings；② SETTINGS_ITEMS 移除 genre（8→7）+ 左栏属性卡 + 规则弹层；③ GenreSettingForm 面板与 GenreHandle 契约退役。
    1. 为什么这才是「正确的想法」：awesome-novel 里作家与题材的全部交互 = init 时挑一个编号。它没有题材面板、没有确认按钮、没有规则表单——规则是 AI 的知识，不是人的待办。v1 保留了面板，就还是让作家「处理」题材。
    2. 砍 UI 是认账的减法：重度作家暂时失去精调 19 行的入口。依据：预置规则与 awesome-novel 同源已足够好，作家几乎从不改（改了也多为误伤）；数据未删，API 原样，未来按真实需求做规则包。真想影响输出的作家有正路——「风格」与「AI痕迹控制」面板。
    3. 设定流反而更完整：7 项全部是创作决策（简介/主线/世界/风格/AI痕迹/伏笔/角色），没有一项是「替 AI 确认它早就知道的事」。第一步从「选题材」变成「写简介」，进书即创作。
    4. 顺手清掉的旧账：「换题材会重置精调规则但 toast 说保留」的误导文案、题材面板的确认语义与进度口径纠缠——随面板退役一并消失。
    5. 遗留两笔（不在本期）：故事骨架终局归「主线」面板（需后端把 selected_arc_id 迁出 genre 记录）；「无题材写作」自由派作家的兜底（可选「暂不选」，属性卡明示影响范围）。

    拍板后建议：① 在 prototypes/ADJUSTMENTS.md 登记 book.html 原型同步（设定 7 项 + 属性卡）；② openspec 立项（实现仅涉 client/frontend 呈现层与建书弹窗，payload 契约零改动）。本稿不改动 prototypes/ 与任何实现代码。
