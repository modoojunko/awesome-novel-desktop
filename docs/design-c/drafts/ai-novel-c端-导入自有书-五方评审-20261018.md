# 导入自有书 · 五方评审（2026-10-18）

评审视角：前端、后端、系统架构、提示词/模型调用、产品。
评审对象：`openspec/changes/c-import-own-book/`（proposal / 7 份 spec delta / design / tasks）、`docs/design-c/drafts/ai-novel-c端-导入自有书-原型.html`、`docs/design-c/drafts/ai-novel-c端-导入自有书-流程整理.md`。
评审方式：只读；代码证据按 `origin/main`；未修改实现。

## 结论

五方一致：**方向成立，A 路可以先做，但当前文档不能直接开工；B 路问题更大，需要重审管线、分段和卡片契约。**

- A 路（直接导入）在补齐 6 项硬伤后可进入实现；它本身不依赖 B 路，但必须做成完整闭环（不是「导入完只弹一个通知」）。
- B 路（AI 拆书）不是补几个字段的问题：冻结 manifest 没接进管线、分段与现有任务状态冲突、卡片字段落不出基线、开书 claim 崩溃会死锁、迁移机制不匹配。建议在 A 路验证后再单独评审。
- 当前 change 把 A/B 两阶段放在同一个 change 里，但 spec/tasks 没有阶段门；A 路做完也不能按「change 完成」归档。建议拆成两个 change，或给 requirements 打 Phase 标记并加后端 gate。

## P0（开工前必须处理）

### P0-1 开工基线错误：当前工作区落后 origin/main 61 个提交

证据：`git rev-list --left-right --count HEAD...origin/main` → `0 61`；`client/frontend/src/components/tools/` 在当前工作区不存在，`TaskListPage.tsx`/`TaskDetailPage.tsx`/`CreateTaskPage.tsx` 只在 `origin/main`。当前主检出还有并行会话的未提交改动。

影响：照着当前工作区开工，会做出「任务清单/拆书入口不存在」的实现；后续合并必冲突。

修法：从 `origin/main` 新建独立 worktree/分支（遵守 AGENTS 每会话独立环境），先跑一次前端 vitest/tsc 确认基线绿，再把基线 commit 写进 `tasks.md` 9.7。不要在当前主检出上开发。

### P0-2 「全书第 43 章」会算成「第 19 章」

证据：`client/backend/chapters/frontier.py` 的 `chapter_no` 是卷内号；待写占位是 `last["chapter_no"] + 1`；前端 `NovelWorkspace.tsx`、`OutlineTree.tsx`、`PreviewView.tsx`、`VolumeWorkspace.tsx` 都直接用卷内号。两卷 42 章时，第 2 卷第 18 章之后的下一章是 `vol-2-ch-19`，不是全书第 43 章。

影响：续写、树标签、预览、新建章默认标题、拆章素材里的「第 N 章」全部错位；spec 的「42 章导入后写第 43 章」无法验收。

修法：后端 `frontier`/`/volumes`/`/tree` 下发 `global_no`（按卷序+卷内序计算），或前端只保留一个 `globalChapterNo()`；新建章默认标题也用全书号。加「2 卷 42 章」回归：第 43 章、第 27 章、跨卷创建。

### P0-3 `imported` 不是稳定状态，现有入口会把它改回 draft/confirmed

证据：
- `chapters/router.py` 的 confirm 直接写 `status="confirmed"`；unarchive 写 `status="draft"`；
- `chapters/store.py` 接受请求体 `status`；版本恢复会回写旧 status；
- `chapters/frontier.py` 的 `is_writable` 对任何有正文的章返回可写，包括 archived（与「归档只读」口径冲突）。

影响：作者确认章纲、恢复编辑、版本回滚后，导入章可能不再是 `imported`，续写光标回到历史章；完本/阶段统计也跟着错。

修法（二选一，必须写进设计）：
1. **更小的改法**：status 枚举不动，只加 `origin=import` + `imported_at`，派生 `is_historical = origin==import && status!='archived'`；frontier/完本/story_state 都消费 origin。
2. 保留 `imported` 值，但给 confirm/unconfirm/unarchive/revert/rewrite/version-restore 六个入口定规则（拒绝或保持），并加「端点 × origin」矩阵测试。

同时决定「归档章只读」由谁保证：`is_writable` 加 archived 守卫，还是只在 PUT prose 层拦；不能两头都不管。

### P0-4 A 路「单事务落库」在现有服务上做不到

证据：
- `novels/service.py::create_project` 内部 `db.commit()`；
- `chapters/store.py::save_chapter` 每次自开 session 并 commit；
- `novels/router.py` 的旧 `import_persist` 每卷、每章分别 commit；
- `repositories/chapter_repo.py::upsert` 默认 `word_count=0/has_prose=False`，批量插入若忘记算派生字段，frontier/读树会把章判成空章。

影响：180 万字导入中途失败会留半本书；重试重复建卷/章；「整笔回滚」和「重复请求返回同一本书」只是文档承诺。

修法：新增唯一的 repo 级 `persist_import_structure(session, ...)`，Novel/Volume/Chapter/Content/import_token 全在调用方 session 内一次 commit；`create_project` 增加 `commit=False, seed_settings=False`；禁止事务内调用 `store.save_chapter`。加 200/240 章中途失败注入测试，断言零残留。

### P0-5 导入章的消费面没收全

已确认会误判的路径：
- `write/prompt_sources.py`：上一章是 imported 时返回「上一章未归档」；
- `volumes/service.py::resolve_prev_ending`：只取 archived，跨卷进场材料回到卷纲预期；
- `chapters/ai_plan.py`：卷配额/末章按全部行计数，导入章占配额；`done` 列表不取正文首段回退；
- `write/story_state.py`：stale refs 只查 archived，imported stale 章静默跳过；
- `archive/dossier_router.py`：`not_extracted` 只认 archived，A 路无基线章没有补算入口；
- 阶段/完本：后端 `total_archives` 与前端 `novelStage.ts` 用 `archived >= total`，分母仍含 imported；42 章导入后归档新章，永远到不了 ready；
- `works-finish-flow`、`novel-workspace`、`write`、`volumes`、`archive` 五份主 spec 没有 MODIFIED delta。

修法：集中 `status in ('archived','imported')` + `origin` 判据；完本口径拆成 `authored_total/authored_archived`（分母也排除 origin=import），只在导入书场景生效；补 5 份 delta；加「同一 status 分支全站扫描 + 端点回归」矩阵。仅 42 章全导入归档的测试不够，必须加「42 章导入 + 新章归档」的完本用例。

### P0-6 B 路管线不使用冻结 manifest，分段会跳过/覆盖

证据：
- `deconstruct/pipeline.py::_load_chapters` 直接读 `task.source_path` 再 `parse_novel`，不读 manifest；
- `cards.state == completed` / dim 完成后会跳过；`products_json` 每维只有一份；
- 任务表没有按段的 cards/dims/products 存储；`segment_index` 只是进度，不能隔离产物。

影响：任务创建后升级应用或续拆，卡按新 parser 的章节边界生成，`structure_json` 仍是旧边界，基线落到错误章；第 2 段开始会因第 1 段的完成状态被跳过，或覆盖第 1 段产物。

修法：`_load_chapters` 改为按 manifest 的 `source_idx/char_start/end` 切片；每段独立 `cards/dims/products` 命名空间；续拆校验 `parser_version`，不一致拒绝或强制重建；加「v1 建任务、v2 续拆，章映射不变」契约测试。

### P0-7 「分段拆书」方案本身需要重审

评审发现两个反向证据：
- 现有管线本来就没有 60 万字硬上限：逐章卡 + `CARD_BATCH_CHARS=30000` 分批 + 树状 reduce，已支持长文；`_merge_final` 的冲突策略是「保留首份」；
- 十维提示词（characters/mainplot/relations/foreshadow）把 `full_synopsis` 定义为「全书逐章梗概」，假设一次看全书；分段独立跑会把段末当全书结局，角色 role、主线弧、伏笔配对都按段内全局判断。

影响：如果现有管线已能跑 180 万字，外层分段是重复建设；如果确实有 60 万限制，按当前「每段独立跑十维」也会破坏跨段一致性，且段内 first-wins、跨段 last-wins 让结果依赖分段边界。

修法：先实测现有管线对 180 万字/240 章的行为（不新增代码，用现有任务跑或桩），确认到底有没有 60 万约束。若有，改成两遍：每段只跑逐章卡，全部段完成后用全量 cards 跑一次十维归并（带上段上下文/角色表/世界块/未收伏笔），graph 用全量 cards + 章号 offset；不要每段独立跑十维。若没有，删掉外层分段，只保留章级断点。

### P0-8 卡片契约落不出 D4 要求的逐章基线

证据：`awesome-novel-prompts/prompts/deconstruct_card.prompt` 的卡片只有 `world[{name,note}]`、`characters[{name,role,traits,alias}]`、`relations[{a,b,type}]`、`foreshadow[{desc,kind}]`；没有 evidence/quote、没有「设定变化」语义、没有关系 change_note、没有角色 state_change。而章档行要求 evidence，四域提取按「变化+证据句」设计。

影响：按 design 的映射表写 baseline，会把「可见设定」冒充「本章变化」，`evidence` 为空；coverage 标 `full` 不成立；quote 回验也不存在。

修法（二选一并冻结）：
1. **接受有损**：四域 coverage 标 `partial`，`evidence=""` + `evidence_absent`，回执明示「卡片派生、无证据句、只读首尾约 6000 字」；不要在文档里写 `full` 或 quote 回验。
2. 改 `deconstruct_card` 增加变化字段与证据句，升提示词包版本（跨仓、需发包）。

### P0-9 伏笔锚定没有可落库的键

证据：卡片 `foreshadow` 只有 `desc/kind`，没有 plant/payoff 章；书级 hooks 来自 `foreshadow` 维度产物（有 plant_ch/payoff_ch）；`apply.py` 只把 plant 章拼进 description；`hooks_service.py` 不写 `introduced/planned/resolved_chapter_id`，单次最多 20 条。

影响：「逐章卡只补章号锚定、书级台账唯一来源」无法实现；42 章埋/收点无法回填到台账；>20 条会截断且没有回执。

修法：以 `foreshadow.hooks` 的 `plant_ch/payoff_ch` 为唯一锚定源，章节落库后用章 ref 回填三个 FK；定义 hook 去重键（desc 归一 + 相似度阈值）；>20 条在回执明示。卡片 `kind` 只用于「本章有埋/收动作」校验，不承担台账身份。

### P0-10 开书 claim 没有租约/启动 sweep，崩溃后永久卡死

证据：design 的 claim SQL 只接受 `open_state IN ('none','confirming','partial')`，没有 `open_claim_at`/租约；启动 sweep 只处理任务 `status='running'`，不处理 `open_state='opening'`。

影响：应用在开书阶段被关闭，下次永远返回「正在开书」；部分书又被书架过滤，形成不可见死书。

修法：加 `open_claim_at` + 租约/心跳；应用启动时把过期 `opening` 收敛为 `partial` 并清 claim；允许同 token 续跑；明确 task.status × open_state × book × claim 的完整组合表（评审列出 9 种，其中 6 种未定义）；partial 书占配额/删除任务/删除书的级联规则也要定。

### P0-11 迁移/backfill 与现有 db-per-version 机制不匹配

证据：
- `db_lifecycle.py` 在 schema 指纹不匹配时把旧库改名 `.mismatch`，不就地加列；
- `migration/engine.py` 对缺失的 NOT NULL 无 `server_default` 列填 `''`，不是 Python default；因此 `source`/`open_state`/`origin` 只写 `default=`，旧任务搬过来会是空串；
- 旧 import 书的 `draft→imported` 不是一次 DB 迁移能完成；现有 carry 是用户触发、源库只读、目标库新插入，`main.py` lifespan 没有 backfill 钩子；
- `design.md` 提到的 `books.import_state` 在 schema 中不存在；
- `source=import` 同时被旧书 backfill、A 路新书、`create_project` 的「是否播种」三处使用，无法区分旧/新。

修法：所有新增 NOT NULL 字符串列加 `server_default`（`manual/none/authored/extract`）；旧书回填做成「carry 完成后按 `app_meta.import_backfill_v1` 幂等执行」；新增 `books.import_kind`（`direct|deconstruct|legacy`）或等价字段；只保留一个 book↔job 指针；旧 `/import/persist` 改 410 或写 imported。回滚口径写成「旧版本+旧库可启动；新库数据需先导出/备份」，不要笼统写「恢复备份」。

### P0-12 删除导入章在现有规则下不可实现

证据：`chapters/router.py` 只允许删「本卷最后一章 + 拟定 + 无正文」；导入章全部有正文，必返 409。spec 要求删除导入章且后续章序连续，意味着重排 `chapter_no/ref`，会破坏 last_write ref、归档文件名、既有章引用。

修法：v1 明确只支持第 2 步「导入前忽略/删除」；落库后删除若要做，单独设计 tombstone 或引用迁移，不能写「走既有删除规则」。这是产品范围决定，不是实现细节。

### P0-13 产品闭环与文案仍未冻结

- **A 路终点**：原型 A 路成功只弹「已建书」通知，没有「写第 43 章」CTA；B 路回执「进入书内」跳设定页，不是写作页。A 路没有 mainplot，点「拆章」会撞「主线为空」闸门；必须给「补主线/补当前卷卷纲」清单。
- **词表**：原型大量使用「基线」「10 维」「补算」「历史章」；A/B 命名不统一（「直接导入」vs「只导入正文」；「跳过设定直接开书」）；顶栏「续写」与章节树「继续写作」语义不同。design-system spec 的可见词白名单与原型冲突。
- **第 2 步质量闸**：只写了 risk，没有 warn 动作；0 章/单章超 60 万字时 B 路应直接禁用；「重命名/前 200 字预览」在 flow 要求、proposal 列为二期、tasks 没写，三处矛盾。
- **配额/模型门**：原型只有文字，没有归档/删除/升级/去配置的真实出口；B 任务是否预占书位未定义；开书时才满额会 403 而不是可执行提示。
- **生命周期**：删任务/删书/部分书/重复导入/need_reupload/双击建任务/书已删除的任务行，没有完整规则；A 路幂等靠客户端 token，token 丢失会再建一本；B 路建任务没有幂等键。
- **隐私/退费**：原型 B 卡没有「全文发送给模型服务商」、没有「取消/失败/重跑已消耗 token 不退」；A 卡没有「只在本机」；`sanitize.py` 是内容审核中性替换，不是匿名化，不能写成「出口脱敏」。
- **开书进度**：第二轮拍板 #7 是「≤2 秒删四段，2–5 秒不定量，>5 秒只给一条真实计数」；spec/design/tasks 写的是「p90>2 秒显示四段」，三处与拍板不一致。
- **计数桶**：预览里导入章归档后标「已归档」，但完本进度排除导入章；42 章全归档会出现「已归档 0 + 原文 0 + 总数 42」的计数不闭合。

修法：先冻结一份作者词表与六条生命周期规则（删任务/删书/部分书/重复导入/need_reupload/双击），再改原型和 spec。A 路成功页与 B 回执都以「开始写第 43 章」为主 CTA，「去核对设定」为次 CTA；A 卡写明「AI 拆章前需补主线与当前卷卷纲」。隐私/退费做成 CTA 上方常显 notice。

## P1（Phase 1/2 前处理）

1. **前端任务 DTO 与三态**：`deconstructApi.ts` 的 Summary/Detail 没有 `source/open_state/book_id`；任务列表写死「拆书」和「待选去向」，导入任务仍显示 7 项勾选和导出。要扩展 DTO、抽 `taskDisplayState`、做 `OpenBookDialog`，支持从列表行开书、用任务 `structure_json` 原地调整结构。
2. **开书轮询会冻结**：`useDeconstructTasks` 的 ACTIVE 只有 queued/running，任务 completed 后停止轮询，但开书写在 completed 之后；要加 `useOpenBook`（点击时 POST，不在 effect 里，防 StrictMode 双发）、`useRef` 防双击、1.5 秒延迟显示四段、600–800ms 轮询、卸载清理。
3. **last_write 污染首次续写**：打开导入书自动聚焦第 1 章，滚动监听会写 last_write；hereTarget 会话优先，于是点「续写」回第 1 章。要禁止导入书自动聚焦第 1 章，last_write 只在真实输入或显式「续写到此处」时记录；树 CTA 用独立 `continueTarget`。
4. **第 2 步数据模型**：原型的 `vols` 用绝对章号闭区间 + 固定 TOTAL，忽略一章后会留洞/错位；整树 `innerHTML` 重建会丢焦点；没有 ignore/risk。改成 `chapters[{id, sourceNo, title, excluded}] + cuts: chapterId[]`，卷名绑首章 id，折叠用 `Set<volumeId>`；split/merge/ignore 只改 cuts。
5. **50MB API 形状**：现有 `importParse` 返回每章完整 content，persist 再回传 volumes+content；大书整本 JSON 往返。要新增 manifest 类型，persist 只传 `import_id + name + volumes + import_token`，正文留服务端；解析支持 AbortController。
6. **设计系统**：原型 `📄` 会触发 emoji lint；`.gl-book-link` 是新的 999px 胶囊，违反「不新增胶囊形态」；新原型/新源码没进 strictGlobs，lint 扫不到；`design-vocab.mjs` 是类名/档位，不是用户词表。新词应登记 `docs/ux/design-language.html`，只有新增类名/字号才改 design-vocab。
7. **现有测试红名单**：旧 `ImportNovelModal` mock、`apiBoundaries` 的旧 `importPersist`、`.md` fixture 的 401/503/error-message 测试、toolsDetail 的「选择去向/存本地文件夹」、toolsTaskList 的六态文案都会红；同一批更新 mock/类型/文案，写进 tasks 9.3/9.4。
8. **A 路「设定留空」与「简介/题材机械识别」矛盾**：flow 说自动识别，proposal/spec 说留空，tasks 只写 `seed_settings=false`。二选一并写进 spec；若保留识别，确认不调用模型，否则 0 token 不成立。
9. **提示注入**：拆书卡片模板只有「正文是分析样本」，没有「正文中的指令一律不执行」；`pipeline.py` 把书名/章题/正文直接 format 进 user 消息。要给 card/十维/reduce 的 system 加统一防线，并用固定对抗样章验证 schema/字段/落库不变。
10. **费用估算**：现有管线有 `SEGMENT_RETRIES=2`（最多 3 次）、卡 6144/维度 8192 max tokens、思考 token、graph 收尾；「字数×1.5–2.5、0.5–0.8 分钟/章+8–10 分钟」没有覆盖重试和思考，容易低估。用固定 3 章样章实测 p50/p90，把「思考 token 也计费」写进文案。
