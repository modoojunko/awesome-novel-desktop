C端 版本号常驻落点

前置口径：版本号已拍板「要常驻可见」（否决「只放设置弹窗」）；本稿只裁定常驻落点选哪。账号展示维持已批方案（设置弹窗账号行「用户名 · 套餐」），本稿所有顶栏均不含账号信息。

  • 文案口径：正式版用短版「v0.15.1」（顶栏 / 状态条等小空间）或全称「爱小说桌面版 v0.15.1」（窗口标题等宽松空间）；dev 态显示「开发版 dev」、获取失败显示「版本未知」，稿中不专门表现。
  • 读图方式：下方每个模拟窗口里虚线框圈出的 v0.15.1 就是该变体新增的版本号元素，其余部分为现状复刻（顶栏结构、尺寸与 list.html / book.html 逐字一致）。
  • 顶栏两个变体：常规（logo + 导航 + 客服 + 设置）与工作台（logo + 分隔线 + 返回 + 客服 + 设置）；未登录态顶栏只有 logo + 登录 + 免费开始。

设计师推荐（供拍板）

推荐 V3 窗口底部状态条；若评审认为工作台 26px 纵向成本不可接受，次选 V1 顶栏右侧小字。V4 建议不作为主落点，但「窗口标题顺手改为爱小说桌面版」无论选谁都可以做。
  1. 为什么是 V3：它是唯一「一处实现 + 顶栏零改动 + 三态无盲区」同时成立的落点。用户的拍板是「版本要常驻」，V3 完整满足常驻，又把需求稿 G3「零新增认知负担、不动顶栏」的代价压到最小——顶栏两个变体和未登录口径一行都不用碰。
  2. 报障场景最稳：状态条是桌面软件的通用心智（编辑器、办公软件都有），「窗口最下面一行右下角」这句话不需要截图就能说清；且未登录、工作台、任何页面位置都不变。
  3. 代价要认账：工作台纵向空间 -26px，写作应用对此敏感——但等宽一行灰字的干扰远小于顶栏加常驻字段；书架页 pagefoot「© 2026 爱小说」需并入状态条左侧（版权行放左边、版本放右边），避免双底条。
  4. 联动裁定建议： ① 若 V3（或 V1 / V2 任一全态常驻落点）拍板，已批 A+ 方案中的「未登录页脚版本行」兜底冗余，建议省略——常驻已全态覆盖，两处重复展示反而显得乱； ② 设置弹窗底部版本行建议保留（PrefsModal / BookPrefsModal 照已批核心做）：它是报障引导的终点，与账号行「用户名 · 套餐」同屏，用户一句话能同时报出版本和账号，成本接近零；若想弹窗最干净也可随本拍板一并取消，二选一即可； ③ UpdateNotice rider「发现新版本 vX（当前 vY）」不受落点影响，照做。
  5. 次选 V1 的启用条件：若产品侧觉得底部状态条「太工程、不像写作工具」，退回 V1——但请接受三个顶栏口径都要动、动作区长期多一个常驻元素的代价，并在窄窗口下回归长书名场景。
  6. 实现注记：版本小字统一 mono + tabular-nums、muted、11.5px；数据沿需求稿口径 quiet 调 /update-check 取 current，失败静默显示「版本未知」；建议挂 data-od-id（本稿已示范 navbar-version / logo-version / statusbar-version / window-title-version）。

拍板后建议：随落点一并裁定「未登录页脚兜底去留」与「弹窗版本行去留」（见上 ①②），并在 ADJUSTMENTS.md 登记对应原型修订；本稿不改动 prototypes/ 与任何实现代码。
