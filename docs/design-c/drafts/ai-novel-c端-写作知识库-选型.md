# 写作知识库 · 选型（C端 · 2026-10-30）

**一句话**：在「本地单机、单人、千条级、已有 SQLite、已有拆书十维」这四个约束下，选**L0 元模型（轻量 property graph＋概念 schema 注册表）→ L1 六概念 → L2 题材实例 → L3 派生视图 → L4 消费**；存储用统一实体表＋按概念校验的 JSON 载荷＋关系表＋标签索引；检索用确定性筛选。派生库用**显式圈选 join**（规则只做一次性物化），消费用**进程内契约函数**，快照用**三方差异合并**。不引入向量库、不引入独立服务、不引入每类型一张表。

配套：整体方案 `ai-novel-c端-写作知识库-整体方案.md`；手法库细化 `ai-novel-c端-手法库-设计说明.md`。

## 0. 决策总表（先看这个）

| # | 决策点 | 选择 | 一句话理由 |
|---|---|---|---|
| 1 | 知识模型 | L0 元模型（实体/关系/属性/约束/证据/视图/契约/版本）＋L1 六概念 | ontology 方法论；概念是注册表，作家只填实例 |
| 1b | P0 概念 | 文风 / 文笔 / 世界 / 角色 / 手法 | 五个都有现成落点（style/world/角色卡/user 提示词）；情节 P1 |
| 2 | 条目存储 | 单表 `kb_entries` ＋ `payload_json`（按 concept 校验）＋`kb_relations` | 跨概念检索/派生是核心；关系要可查；分概念表会把 join 和迁移放大 |
| 3 | 多维标签 | `kb_entry_tags`（entry_id, dim, value）索引表 | 题材/场面/情绪是热过滤，tag 表可索引、可计数 |
| 4 | 检索 | 结构化筛选＋FTS5（可选）＋确定性排序 | 千条级、要可解释、要离线；向量留 P1 |
| 5 | 概念/题材 | L1 固定六概念＋L2 题材分区＋受控 facet＋自由 tags | 概念是类，题材是实例分区；LLM 只建议不自动写 |

| 8 | 快照同步 | 三方差异（启用基线 / 当前库 / 本书覆盖）＋默认只加不改 | 保护作家手改；库更新不静默改书 |
| 9 | 前端 | 全局「写作工具 → 知识库」＋**题材左栏＋分类页签**＋书内来源行 | 账号级资产不进书内一级页签；题材是作家的第一直觉 |
| 10 | 备份 | 账号五表进配置包；书内三表随单书 | 与角色库同槽；单书恢复不依赖库在线 |

## 1. 选型前提

| 约束 | 数值/事实 | 对选型的影响 |
|---|---|---|
| 单机单人 | 无并发写、无多租户 | 不需要服务化、分布式锁、跨端同步 |
| 数据量 | 条目 1k–5k；库 10–30；书 100 章以内 | 全量内存打分可行；不需要分页游标之外的花活 |
| 既有存储 | SQLite（`python:3.12-slim`，aiosqlite） | 不引入第二套存储；JSON1/FTS5 可用（FTS5 启动探测） |
| 既有能力 | 拆书十维、文风/世界 KV、手法匹配、角色库（在途） | 选型必须复用这些出口，而不是另建 |
| 硬约束 | system 逐章字节一致（prose-writing spec） | 文风/世界只能快照进设定，不能逐章动态 |
| 版权口径 | 不存原文语料 | 条目只存指令/特征；证据只读；示范段走既有 6×500 通道 |
| 组织方式 | 一本一个主题材；题材词表既有 | 题材是 L2 实例分区；条目一个主题材＋少量题材标签 |

## 2. 分类选型（P0 放哪四类）

评分：消费链是否现成（0–3）、供给源是否现成（0–3）、验收成本（越低越好）、独立价值。

| 分类 | 消费链 | 供给源 | 验收成本 | 结论 |
|---|---|---|---|---|
| 文风 | style.role/samples/fewshot → system 文风基线（已有） | 拆书 style | 中（快照＋同步差异） | **P0** |
| 文笔 | style.rules/craft/banned/tic → system 文笔基线（已有） | 拆书 style | 中（快照＋同步差异） | **P0** |
| 世界设定 | world KV → system 世界观（已有） | 拆书 world | 中（分区映射＋冲突） | **P0** |
| 角色设定 | 角色卡起草（角色库在途） | 拆书 characters / 角色库 | 中（复制落卡，不写正文） | **P0**（P0-D） |
| 手法 | 正文 user 层（已有落点，新增一节） | 拆书 techniques | 中（匹配清单＋反馈） | **P0** |
| 情节套路 | 剧情抽卡/推演（弱） | 拆书 mainplot/structure | 高（需要新的消费面） | P1 |

判断规则：**没有稳定落点的分类不放进知识库首页**。否则首页会变成「五种表单」，而作家感受不到任何产出。角色设定之所以能进 P0，是因为它有现成的角色卡/角色库落点（复制落卡），不需要新造消费面。

**题材不在这张表里**：题材是五类之上的第一层（档案柜），不是第六种分类。

## 2.5 知识模型（ontology）选型

这一节回答「知识库的元模型怎么建」，与存哪个数据库无关。

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. EAV（实体-属性-值） | entity/attribute/value 三表 | 无限扩展 | 查询要 pivot；类型约束弱；一条知识几十行 | 否 |
| B. 轻量 property graph ＋ 概念 schema | 实体表（payload JSON）＋关系表＋标签表；概念 schema 在代码 | 扩展只加 schema；关系可查；SQLite 单文件；可解释 | 关系遍历要自己写（无 Cypher） | **选 B** |
| C. RDF/OWL ＋ 推理机 | 三元组＋本体＋reasoner | 形式化最强；可推理 | 工具链重、无本地小型 reasoner、作家不可见、性能差 | 否 |
| D. 纯文档（JSON 文件） | 每条知识一个 JSON | 无 schema 负担 | 无关系、无事务、无检索 | 否 |
| E. 每概念一张表 | 文风表/世界表/角色表… | 强 schema | 新概念=建表+迁移+备份段；跨概念列表 UNION | 否 |

**B 的方法论**——ontology 的六个构件全部落在 SQLite：

- **类 Class** ＝ L1 概念注册表 `CONCEPTS`：文风/文笔/世界/角色/手法/情节，每个有 `schema / relations / quality_rules / renderer / contract`。
- **属性 Property** ＝ `payload_json`，按类的 schema 校验；`payload_version` 管演进。
- **关系 Relation** ＝ `kb_relations`：`refines / contradicts / depends_on / instance_of / derived_from / applies_to`。
- **实例 Instance** ＝ `kb_entries`：`(genre, concept, payload)`。
- **视图 View** ＝ `kb_libraries` ＋ items：按用途圈选；不是类，也不是实例。
- **约束 Constraint** ＝ Pydantic validator ＋ 消费前检查（必填、基数、值域、互斥）。
- **证据 Provenance** ＝ `evidence` 列。

**不做的事**：不做推理机（没有 transitive/sameAs 推理需求）；不做用户自定义概念（概念是开发者注册表，作家只填实例）；不做 RDF 序列化（本机单文件，不需要交换格式）。

## 3. 存储形态

### 3.1 候选

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 单表＋JSON 载荷 | 跨类型检索/派生简单；新类型只加校验器；迁移只加列 | payload 结构易漂移；查询要校验版本 | **选 A** |
| B. 每类型一张表 | 强 schema；单类型查询直观 | 跨类型列表要 UNION；派生跨表；每加一类型=建表+迁移+备份段 | 否 |
| C. 文档库（JSON 文件） | 无 schema 负担 | 事务/备份/并发/查询全要自己写；与既有 SQLite 不一致 | 否 |
| D. 外部分类服务 | 语义能力强 | 违反离线/本地/单人前提；引入运维 | 否 |

### 3.2 A 的落地

```sql
kb_entries(
  id, user_id, genre, concept, title,
  payload_json,        -- 按 concept 的强校验载荷（Pydantic 写入前校验）
  payload_version,     -- 结构演进用；读取时按版本迁移
  instruction,         -- 通用检索/渲染列（写法=怎么写；文风=一句声音；世界=一句设定；角色=一句原型）
  negative_example,    -- 通用列（没有则空）
  evidence,            -- 来源证据（只读、≤800 字、不进提示词）
  status,              -- active/paused/archived
  src_kind, src_ref, src_key, src_novel_name,
  created_at, updated_at
)
kb_relations(from_id, to_id, rel_type, note)  -- 关系原语
kb_entry_tags(entry_id, dim, value)   -- dim ∈ genre | concept | scene | emotion | slot | tag
-- 索引 (user_id, genre, concept, status)；题材计数/概念计数都走 tag 表
```

- **payload 按 concept 校验**：`CONCEPTS = {"文风": ..., "文笔": ..., "世界设定": ..., "角色设定": ..., "手法": ..., "情节": ...}`，写入前 Pydantic 校验；未知 concept 拒写。
- **标签表是索引，不是事实源**：payload 里保留原值，标签表由服务层在同一事务内重建（条目编辑时删旧插新）。这样过滤/计数/派生规则都走索引，payload 仍可完整回放。
- **不做 JSON 列上的高频查询**（JSON1 可用，但不作为主路径）；热点过滤一律走 `kb_entry_tags`。

### 3.3 为什么不做每概念一张表

加一个概念要动：模型、迁移（列交集会跳过 NOT NULL 新表）、备份段、前端表单、消费契约。单表的代价是 payload 校验器，收益是「新概念 = 新校验器 + 新渲染器」，与产品「派生新库」的演进方向一致。

## 4. 检索

| 方案 | 能力 | 成本 | 结论 |
|---|---|---|---|
| A. 结构化筛选（题材/kind/tags/来源/状态） | 精确、可解释、毫秒级 | 低 | **P0 主路径** |
| B. FTS5 全文（标题+指令+证据） | 中文分词弱（默认 unicode61 按字切），但足够搜关键词 | 低；需建虚表/触发器 | **P0 辅助**（启动探测，不可用则 LIKE） |
| C. 本地向量（sqlite-vec / ONNX embedding） | 模糊召回强 | 中高：模型体积、首启下载、索引版本、结果不可解释 | P1 |
| D. LLM 语义筛选 | 最懂意图 | 每查一次烧钱；不确定；离线不可用 | 否（日常检索） |

**P0 组合**：题材 → 分类 → `tags` 精确过滤 → FTS5/LIKE 关键词 → 确定性排序（来源权重、最近使用、留用率）。**P1**：向量只做「找相似条目」的辅助，不替代硬条件；混合排序，向量分只占一档。

FTS5 探测：启动时 `CREATE VIRTUAL TABLE IF NOT EXISTS kb_fts USING fts5(...)`，失败则降级 LIKE；不把 FTS5 作为硬依赖（打包环境差异）。

## 5. 分类与标签

| 维度 | 来源 | 受控？ |
|---|---|---|
| concept（L1 类） | 固定六类：文风/文笔/世界设定/角色设定/手法/情节 | 是（注册表白名单） |
| genre（L2 分区） | 既有题材词表（`genres`/`genre_vocab`）；一个条目一个主题材 | 是（复用，不新造） |
| scene | 八档：开篇/过渡/日常/冲突/打斗/文戏/揭秘/高潮 | 是 |
| emotion | 六档：燃/爽/甜/虐/悬/平静 | 是 |
| slot | 文风：role/samples/fewshot；文笔：rules/craft/banned/tic；世界：8 键（7 分区＋no_power）；角色：档案八格 | 是（按 concept） |
| tag | 自由词 | 否（作家可加） |

LLM 只在**导入时建议**标签（从拆书证据里推），建议要作家确认才落库；不在检索时用 LLM 分类。理由：概念/题材体系一旦让模型自由发挥，派生规则和覆盖度统计就失去基准。

## 6. 派生库

| 方案 | 说明 | 结论 |
|---|---|---|
| A. 显式成员 join | 作家勾选/移出；顺序可排；库稳定 | **选 A** |
| B. 复制条目进库 | 库内改不影响原条目 | 否：同一知识多份副本，改一处漏一处 |
| C. 纯查询视图（规则实时算） | 零维护 | 否：规则一改成员漂移，作家昨天看到的库今天变了 |
| D. 规则一次性物化 | 点「按条件圈」→ 预览 → 确认后写成显式成员 | **P1**（P0 手选；D 是 A 的批量入口） |

**库带题材＋概念**：`kb_libraries.genre` 与 `.concept` 是库的作用域；书只启用自己主题材的库；同题材同概念互斥。

**库的 rev**：成员增删、条目编辑（影响渲染）、顺序调整都让 `rev+1`。启用快照记 `rev` 与成员 id 列表；同步差异用 `rev` 快速判断「有没有变」。

**同题材同概念多库**：允许（仙侠·冷硬派文风 / 仙侠·古风文风）。P0 默认每个题材每个概念一个库，命名不占用；派生弹窗允许同名不同 id。

## 7. 消费编排

| 方案 | 结论 |
|---|---|
| A. 进程内服务＋纯函数渲染 | **选 A** |
| B. 独立微服务 | 否：单机单人，多一个进程/端口/健康检查没有收益 |
| C. 事件总线/异步队列 | 否：同步消费，失败要立刻反馈；手法生成本来就在请求内 |

五条契约：

1. **live（手法）**：`match(entries, brief, prefs) -> items` 纯函数；`render(items) -> block` 纯函数；写 run 快照是唯一副作用。
2. **snapshot（文风）**：`render_library(entries) -> voice_slots`（role/samples/fewshot）；三方差异；一次事务写 `style`。
3. **snapshot（文笔）**：`render_library(entries) -> craft_slots`（rules/craft/banned/tic）；三方差异；一次事务写 `style`。
4. **snapshot（世界）**：`render_library(entries) -> world_slots`；三方差异；一次事务写 `world`。
5. **draft（角色）**：`render_prototype(entries) -> character_draft`；只读，作家确认后复制落角色卡；不回写库。
6. **draft（情节，P1）**：渲染成抽卡/推演的输入，不落库。

**事务边界**：启用/同步在单事务内完成「读库→渲染→写 KV→写 binding」；中途失败回滚，书内设定不变。

## 8. 快照同步（三方差异）

三方：

- **base**：启用时写进 `kb_book_bindings.snapshot_json` 的渲染结果（槽位→条目 id→文本）。
- **current**：当前库成员按当前条目渲染的结果。
- **book**：本书当前的 `style`/`world` KV。

合并规则：

| 情况 | 处理 |
|---|---|
| current 有、base 无、book 无 | 新增 |
| current 与 base 不同、book 与 base 相同 | 更新（书没改过） |
| current 与 base 不同、book 与 base 不同 | **保留本书**（默认），列「库已更新，本书改过」冲突行，作家可选采用 |
| current 无、base 有 | **不删除**（默认），列「库里已移除，本书保留」，作家可选移除 |
| 单值槽（如 role）多条 | 冲突，必须选一条；不自动覆盖 |

这套规则的关键是 **「默认只加不改」**：库的演进不会悄悄改掉一本书的声音；作家看到差异，逐条决定。

## 9. 前端形态

| 方案 | 结论 |
|---|---|
| A. 全局「写作工具 → 知识库」＋书内来源行 | **选 A** |
| B. 书内新增一级页签「知识库」 | 否：知识库是账号级资产；书内页签已经 7 个，再塞会挤爆 |
| C. 只在设定页内嵌 | 否：跨书的库没有归属书，且派生/浏览需要大页面 |
| D. 独立桌面窗口 | 否：现有壳层/路由/弹窗体系可复用 |

书内来源行只出现在两个面板顶部：文风（「来自文风库 · 2 条 ＋ 文笔库 · 4 条 · 2 条本书改过」＋去挑/同步）与世界（同）。手法仍在写作页右栏「挑手法」，角色设定在新建角色/角色库的收录面板，不新增书内一级页签。

## 10. 版本、备份、迁移

- **schema**：`models/kb.py` 注册进 `models/__init__.py`；`Base.metadata` 指纹变 → 启动走版本升级；新表列全部带默认值。
- **备份**：账号级 `kb_entries/kb_entry_tags/kb_libraries/kb_library_items/kb_prefs` 进配置包新段；书内 `kb_book_bindings/kb_match_runs/kb_match_items` 随单书备份。
- **格式版本**：`FORMAT_VERSION` 当前 7；与角色库在途单 v8 同批升版（一个号，不各提一版）。
- **payload 演进**：`payload_version` + 读取时迁移函数；旧版本 payload 不改写，渲染时兼容。
- **回滚**：代码回退不读新表；书内设定是快照，旧代码照常读 `style`/`world`，功能消失但数据不坏。

## 11. 性能与容量

| 操作 | 规模 | 目标 | 手段 |
|---|---|---|---|
| 条目列表/筛选 | 5k 条 | <100ms | tag 表索引＋分页 |
| 关键词搜索 | 5k 条 | <100ms | FTS5（或 LIKE） |
| 手法匹配 | 5k 条 × 1 章 | <50ms | 先按书题材缩候选集，再全量内存打分；预取 prefs |
| 库渲染 | 200 条 | <50ms | 纯函数；按 `rev` 缓存 |
| 三方差异 | 200 条 × 3 | <100ms | id 映射＋文本比较 |
| 单章 run 落库 | 8 条 | <20ms | 单事务批量 insert |

容量上限预估：条目 5k × 2KB ≈ 10MB；run 100 章 × 8 条 × 20 本 ≈ 16k 行；SQLite 无压力。**不做**：分库分表、外部索引、缓存服务。

## 12. 安全与版权

- **不存原文语料**：条目只存特征/指令；`evidence` ≤800 字且只读；示范段仍走既有 `style_samples`（6×500）；导入有原文闸（连续 ≥20 字逐字相同即拦截）。
- **不新增密钥**：无新外部服务；模型 Key 沿用现有本地加密存储。
- **数据归属**：知识库随配置包导出；P1 加 Markdown/JSON 单库导出。
- **不联网**：P0 全本地；FTS5/匹配/渲染均无网络调用。

## 13. 被否方案与理由（集中）

| 被否 | 理由 |
|---|---|
| 向量库 P0 | 千条级用不上；模型体积/首启/索引版本/不可解释；先让结构化筛选跑一年 |
| 每概念一张表 | 新概念成本高；跨概念列表/派生要做 UNION；迁移与备份段翻倍 |
| 文件/文档库 | 事务、备份、并发、查询都要自建；与现有 SQLite 体系冲突 |
| 复制式派生 | 同一知识多副本，改一处漏一处；与「条目只有一份」的产品主张冲突 |
| 实时规则库 | 成员随规则漂移，作家无法建立稳定预期；改为一次性物化 |
| 独立知识服务 | 单机单人，多进程没有收益；事务边界反而变复杂 |
| LLM 实时匹配/分类 | 成本、延迟、不确定性；检索要可解释可单测 |
| 书内一级页签 | 账号级资产不该挂在书下；页签已满；打断写作动线 |
| 自动同步库更新 | 静默改书的声音/世界，违背「作家拥有本书」；改为差异预览 |
| 自动改写旧书设定 | 同上；老书必须零迁移、零惊变 |

## 14. 演进路线

1. **P0**：L0 元模型＋L1 六概念＋L2 题材实例＋手法 live＋文风/文笔/世界 snapshot＋角色 draft＋三方差异。
2. **P1**：FTS5 中文优化（自定义分词或 bigram）；按条件圈选（一次性物化）；情节；通用知识；关系视图；同题材同概念多库；库版本回滚；单库导出。
3. **P2**：本地向量混合召回（只做「找相似」辅助）；跨书「知识地图」；库的共享/导入（仍本地文件，不上云）。

## 15. 验收要点（选型落地的机器判据）

- 新增一个概念：只加 `CONCEPTS` 注册项（schema/关系/质量规则/渲染器/契约）＋前端表单，不改表结构、不改迁移、不改备份段。
- 新增一个题材：题材词表加一项；条目、库、派生、过滤全部自动可用，不改表结构。
- 新增一种关系：`kb_relations.rel_type` 加一个受控值；不改表结构。
- 5k 条条目下：题材/分类筛选 <100ms、写法匹配 <50ms（基准脚本）。
- 快照同步：构造 base/current/book 三组数据，三方差异 9 种组合全部按 §8 表落。
- FTS5 不可用环境：启动降级 LIKE，搜索仍可用，不报错。
- 备份：配置包含账号五表（entries/tags/libraries/items/prefs）；单书包含书内三表；恢复单书后即使库缺失，书内设定完整可读。
