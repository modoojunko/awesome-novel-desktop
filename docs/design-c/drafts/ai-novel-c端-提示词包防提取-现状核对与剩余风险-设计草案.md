# ai-novel C端 提示词包防提取——现状核对与剩余风险（草案）

> 2026-10-19 起草。起因：「当前 prompt 是下载下来后本地全部解压，很容易就被人拿到了」。
> 本文先做**前提核对**（这条担心对应的是 2026-10-06 之前的老状态），再画**剩余暴露面地图**，
> 最后给方案空间与拍板项。不是 openspec change；拍板后再立。

---

## 0. 结论（TL;DR)

1. **「下载后本地全部解压、目录随便拷」已经不成立。** 2026-10-06 拍板「不做云拼装、拼装仍在
   本机，但把提取成本抬到高于提示词价值」（`c-prompt-pack-hardening`，已归档＝已合入发版）：
   CDN 上只有密文、落盘是加密容器、钥匙绑机器＋用户、明文只在内存、解密路径编译成原生扩展。
   现在一个**拿到安装包但没账号**的人：一个模板都拿不到。
2. **真正剩下的是三条路**，而且都不是「没做防护」，是架构与产品属性决定的：
   - ① 本档用户脚本解密（登录→换钥→下载→解密，约 20 行代码）——**固有**：他要正常用就必须能解；
   - ② 出口流量抓包（把 API base 指到自己服务器）——spec 明写**不承诺项**，BYO-key 架构固有；
   - ③ 进程内存 dump——spec 明写**不承诺项**。
3. 所以「很容易拿到」对**本档注册用户**仍然成立（①②都是低成本），对**无账号者**不成立。
   这不是执行欠账，是「拼装仍在本机＋用户自带 Key」这条产品路线的逻辑必然。要根治只有一条路：
   **模板不出服务端（云拼装/S端代理生成）**——10-06 已明确拍板不做，翻案是产品级决策。
4. 建议：**接受 1-3 的口径 ＋ 补一层「金丝雀水印·泄露溯源」**（方案 B，低成本高性价比），
   法律条款跟进（方案 E）。云拼装留档观察，出大规模泄露实锤再翻案。

## 1. 前提核对：现状链路逐环列证据

防护链（全部已合入 main，`openspec/changes/archive/2026-10-06-c-prompt-pack-hardening/`）：

| 环节 | 形态 | 代码/依据 |
|---|---|---|
| CDN 分发 | `{tier}.bin` = nonce(12B) ‖ AES-256-GCM 密文；manifest Ed25519 验签 | `client/backend/prompt_pack/sync.py:15-20`（格式契约，与提示词仓 publish.py 对齐） |
| 换钥 | CEK 须登录态向 S端 `POST prompt-pack/key` 换；档位不符 403、密钥退役 404 | `sync.py:302-325` |
| 落盘 | `pack.bin` 加密容器（AES-GCM，AAD 绑版本号）；manifest/receipt 只有哈希无内容 | `client/backend/prompt_pack/container.py`、`prompt_pack/__init__.py`（目录布局注释） |
| 钥匙 | LWK 绑机器＋用户：Windows DPAPI 用户作用域 / macOS Keychain / Linux 机器指纹（弱档，仅 dev/CI）——整目录拷到别机/别户**解不开** | `client/backend/prompt_pack/localkey.py` |
| 明文 | 只在内存，不写任何中间文件；读时按模板文本哈希校验 | `container.py:84-97`、`__init__.py:161-201` |
| 存量迁移 | 旧版明文 `*.prompt` 就地加密后删除明文；失败按未装重下，不留明文可用态 | `__init__.py:204-243`（`migrate_plaintext`） |
| 字节码 | 解密三模块（localkey/container/sync）编译成原生扩展，打包产物 `--scan` 门禁：无模板明文、无钥匙材料的 .py/.pyc | `client/packaging/build/compile_native.py` |
| 对外口径 | spec「本机提取防护强度与不承诺项」：防拷目录/跨机复用/读源码解密；**不承诺**防内存 dump、自建代理抓出口流量、调试器 hook | `openspec/specs/prompt-pack-delivery/spec.md:213-239` |

由此按「谁」分档的获得能力：

- **无账号者**（拿到安装包/扒 CDN）：只有密文。CEK 换不出（要登录）。
- **免费注册用户**：能解 free 档全部模板（这正是给他用的）；pro/max 文件层面换钥 403。
- **付费用户**：能解自己档位全部。

## 2. 剩余暴露面地图（诚实版）

| # | 路径 | 谁 | 成本 | 现口径 |
|---|---|---|---|---|
| 1 | **本档 CEK 脚本解密**：登录→`prompt-pack/key` 换 CEK→下载 `{tier}.bin`→AES-GCM 解密，拿走本档全部模板 | 任何注册用户 | 低（20 行脚本） | **固有可见**（他要正常用就得能解；加密只防「非本档的人」） |
| 2 | **出口流量抓包**：把模型 API base 配到自己服务器，生成一次即得完整 system+user 拼装稿 | 任何能配模型的用户 | 低 | spec **不承诺项**；BYO-key 架构固有 |
| 3 | **进程内存 dump**：容器解密后模板明文驻留内存，调试器/转储可取 | 本机主人 | 中 | spec **不承诺项** |
| 4 | **UI 可见面**：提示词先行编辑流（起草角色等）渲染后 user 段本来就可改可见；系统段不下发不展示（泄漏守卫钉） | 全体用户 | 零 | **by design**（单功能拍板过） |
| 5 | 存稿/日志/回执/书档 | — | — | **干净**：书档只存素材组装稿不存模板（`write/router.py:162-176`——模板只在 `build_system_prompt()` 内存拼装后直发 LLM）；模板文本不进日志（hardening 暴露面卫生条款） |
| 6 | 开发/演示基建：demo 栈 compose 默认挂 sibling 提示词仓明文目录、dev 态直读模板目录 | 开发者 | — | 非交付面（frozen 构建禁用 dev 源） |

**关键判断**：#1＋#2 意味着「任何注册用户都能拿到他那个档位的全部模板」在当前产品形态下
**堵不死**。继续在这两条上加密学手段（更复杂的容器、白盒加密、反调试）都只是提高 #3 的
门槛——而 #3 本来就是不承诺项，收益配不上复杂度。

## 3. 方案空间（赢什么／输什么／我的立场）

### A. 维持现状（零投入）
- **赢**：0 成本；spec 已把口径写死，对外被质疑有依据可引。
- **输**：模板被整档搬走后**无法溯源**；「本档可批量拿走」维持。
- **立场**：底线（提取成本 ≥ 提示词价值）已达标，可接受。这是默认项。

### B. 金丝雀水印＋泄露溯源（**推荐**，低成本）
- 做法：发布链 `publish.py` 按档（可先做到**档位×版本**粒度）对模板注入系统性微变体——
  标点/空格/个别同义措辞，模板本体在提示词仓保持唯一干净源，变体在**发布时**机械生成；
  manifest 记 `variant_id`。容器哈希链天然兼容（每档 bundle 本来就是分开加密的）。
- 拿到一份泄露样本 → 与已知变体比对 → 定位到档位（进一步做 per-account 变体可定位到人，
  但包数×用户数、CDN 与发布复杂度陡增，**先不做**，留作升级手段）。
- **赢**：泄露可取证可定责（竞品扒皮/二次传播有实锤）；事前威慑。
- **输**：防不了「拿去自己用」，只防「传播后被抓」；发布链要改造＋模板 diff 类测试须容忍
  变体（防回归钉要同步调）。
- **立场**：性价比最高的一步。在「防不住拿」的前提下，把「敢传」的成本抬起来，与 hardening
  的成本线思路同构。

### C. 运行期收紧（**不推荐**大做）
- 做法：单模板按需解密不整表驻留、用后即弃。
- **赢**：象征性抬高 #3 门槛。
- **输**：Python 字符串不可变，真正「清零」做不到，只能缩窗口；而 LLM 调用瞬间全文必然在
  内存——对「一次 dump 拿全表」的挡降收益接近零；改动面却覆盖 loader 与全部调用点。
- **立场**：不做；顺手级优化可以，立项不值得。

### D. 翻案做云拼装／S端代理生成（根治，重决策）
- 做法：模板永不下发。C端发素材 → S端拼装 → S端调 LLM → 正文回流。#1/#2/#3 全灭。
- **赢**：模板零暴露；模型与计费官方可控。
- **输**：**推翻 2026-10-06「不做云拼装」拍板**；BYO-key 模式破坏（用户 Key 要交 S端 用，
  或被迫改走官方渠道）；S端承担全部 LLM 流量/并发成本；离线写作不可用；架构级改造。
- **立场**：不建议现在做。留档为「泄露实锤触发再评估」项——若 B 的溯源抓到大规模泄露，
  再回来翻案才有数据支撑。

### E. 法律与条款（配合 B）
- 用户协议明示提示词属我方资产、禁止提取与二次传播；配合 B 的水印做处置依据。
- **赢**：处置链路完整；**输**：事前威慑有限，且走法务（同 tier-plan 有法务闸，节奏慢）。
- **立场**：值得排，但不阻塞 B。

### F. 按次取钥·用后作废（2026-10-19 二轮讨论；**不推荐按字面落地**）
- 提法：「解密公钥放 S端 生成，C端每次组装提示词时请求钥解密，用了后作废」。
  先纠术语：**能解密的钥不能是「公钥」**——公钥人人持有，等于无账号也能解 CDN 包，比现状
  更糟。其实质是「S端托管内容钥、登录态按次签发、签发即记账、用后作废」。按这个语义分析。
- **赢**：
  - 拿到一个**按次观测/限流/可远程切断**的反滥用控制面——BYO-key 下 S端今天对生成用量
    全盲（生成直连用户自己的模型端点），这确实是补观测；
  - 客户端不再常驻内容钥（LWK 退役）。但这条增益≈0：「拷目录到别机解不开」LWK 已做到，
    而「本机主人」从来不是靠偷钥，是靠按次领钥或直接 dump。
- **输**：
  - **三条剩余暴露面一条没堵上**。根本不变量：拼装在客户端 ⇒ 明文必然在客户端出现 ⇒
    钥协议再花哨，机器主人都能在拼装瞬间拿到明文。攻击脚本照 app 的节奏按次领钥即可
    （限流松了没用、紧了误伤重度写手）；自建端点抓包照旧；内存 dump 照旧。
  - **「用后作废」对静态包无意义**：CDN 上的 `{tier}.bin` 永远是同一把 CEK 加密的，任何
    一次签发拿到的都是同一把钥——存一次就永久有效，作废只挡「下次再领」。要让作废有牙，
    得按次/按人重加密内容 ⇒ S端 从「发钥」变「发内容」，静态 CDN 没了 ⇒ 而这一步迈出去，
    S端已经站在每次生成的链路里了，再往前半步就是云拼装（D），防护严格更优、边际成本为零。
  - **离线自持破掉**（spec 保留条款）：每次拼装多一跳 S端（含 30-60s 冷启动口径），
    压在最敏感的生成等待链路上；
  - **S端成本从「按安装」变「按生成」**：QPS 随全体用户用量线性涨，换来的防护增量为零。
- **立场**：这是「付 D 的钱（每次联网），不买 D 的货（明文不出客户端）」。若观测/风控是
  真诉求，用便宜得多的近似——**使用票**：生成前向 S端领一次性票据（登录态＋档位，只记账
  限流不参与解密），解密链路维持现状（离线时领不到票按离线使用后补记账，零 UX 损伤）；
  若「明文不出客户端」是真诉求，就直接做 D，不做半个 D。

## 4. 拍板项

1. 是否确认接受「**本档注册用户可拿走本档模板**」为产品固有属性（现状即如此，spec 已写）？
2. 方案 B（金丝雀水印）是否立项？粒度取**档位×版本**（推荐）还是直接上 per-account？
3. 方案 F（按次取钥）按字面落地的诉求是否存在？若实质是**观测/限流/切断**，是否改用
   「使用票」近似（不参与解密、离线可后补）？
4. 方案 D 是否按「泄露实锤触发再评估」留档，不动？
5. 方案 E 是否随下一版用户协议更新走法务？
