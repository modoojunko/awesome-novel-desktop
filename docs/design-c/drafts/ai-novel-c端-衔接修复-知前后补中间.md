# 设计草案：衔接修复提案——「知前后、补中间」（c-seam-refill）

> 状态：**待拍板立项**（设计稿 v1，2026-10-10）。触发方式：对话里说「立项衔接修复」。
> 依赖：#832（章际衔接检查，已实现待合）＋ #828（去 AI 味修稿向导，已合入）。

## 一、能力定义（一句话）

**检查出章际断点后，修改向导提供「补中间」修复提案**：大模型读着「前」（上章结尾原文＋状态域）与「后」（本章既有后文＋章末落点），只重写断裂的中间段——两侧逐字保留，中间自动长成能接住两边样子。

## 二、为什么是这个（背景与实证）

- 2026-10-10 章际衔接诊断实锤：衔接的「原料机制」是好的（上章结尾块正确），断的是**中间段写跑**（态度跳变、道具断环、开场与上章错位）。
- 现有修复手段的两难：①整章重生成——素材对则从头都对，但**丢掉已写好的段落**（成本 15-70 秒＋好内容重掷）；②手改——作者要自己消化断点证据。
- 被浪费的模型能力：LLM 天然擅长**条件补全**（infill）——给前文与后文，产出与两侧都吻合的中间。「检查（已实现）→ 补中间（本提案）」正好把检测网闭成修复环。

## 三、交互（挂在修稿向导的提案体系）

章际衔接检查（#832）的每条 finding 增加一个动作：**「生成修复提案」**。点击后进入修稿向导既有四步流（检查→提案对照→逐段改→应用），只是提案的类型换成「补中间」：

1. **前**＝上章结尾原文（≤800 字窗口）＋本章断点之前的已写段落；
2. **后**＝断点之后的已写段落＋章末落点（保护：落点是硬边界，后文不许被波及）；
3. **断点描述**＝检查 finding 的证据对（本章原句 vs 对照素材点）＋状态域相关行；
4. 模型输出＝**仅中间段**；前端对照预览：前文（灰，原样）｜中间（高亮，新写）｜后文（灰，原样）→ 逐段改 → 应用。

与去 AI 味的关系：补中间的产物**顺手过 polish 的病灶清单**（同一模型的输出也会带 AI 腔），向导「逐段改」步里复用 polish 快扫，不另起一套。

## 四、提示词草案（新模板 `seam_refill.prompt`，pro 档建议）

```markdown
<<system>>
你是长篇小说的衔接修复师。给你「前文」与「后文」，中间断裂——你只写中间，
把两边严丝合缝地接起来。

铁律：
- 输出只有中间段：第一个字接住前文末句，最后一个字被后文首句无缝接住；
  前文与后文一个字不改、不重复、不总结
- 断点修复优先：按【断点】指明的问题（态度跳变补过渡拍／道具状态补交代／
  开场错位重写接续），修复必须落在中间段内
- 状态域是硬事实：关系温度、物品持有、已得知/仍不知，与【前文】【后文】冲突时
  以它们为准并在中间段内自洽
- 人味纪律：按「人味写法」缺省笔法写（情绪有对象、逗号长呼吸、段尾落物件）；
  不硬造金句、不写解释尾巴
- 长度：能接住即可（通常 2-6 段），宁短勿凑
<<user>>
【前文（原样保留）】
{before}

【后文（原样保留，不可波及）】
{after}

【断点（检查发现，须在本段修复）】
{finding}

【状态域（硬事实）】
{story_state}

【文风】
{style}

只输出中间段。
```

（分责/示例等沿用 polish_text 的成熟纪律；最终以提示词工程师评审稿为准。）

## 七、验收草案

1. 构造断点（改开场/删道具交代）：检查报出 → 补中间提案 → 应用后复检空数组；
2. 前文/后文逐字不变（diff 仅中间段）；
3. 态度跳变类：修复段内出现过渡拍且与关系域一致；
4. 弱模型（deepseek-flash）可用性抽查——补中间对弱模型比全章诊断友好（任务窄、上下文足）。
