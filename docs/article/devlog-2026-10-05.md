# AI写的代码，部署连挂三次

今天解决一个问题，把 GLM 的周额度整个用光了。问题放在发版的最后一步，S端网页的部署，连挂三次，每次都换一种死法。

先交代这个网页是干嘛的。我们的产品除了本地装的应用，还有一套线上页面，授权、付费须知、下载引导都挂在上面，部署在云托管上。发版时要把新构建的页面推上去。今天发 v0.26，安装包、CDN、后端一路顺，最后就剩这一步。

第一次挂，22 秒。部署命令交给云托管的构建机跑，22 秒就报失败。回头查参数，install 那一栏传的是空。tcb 命令行的帮助文档里原文写着，这一栏留空就是跳过安装。空不等于默认，空等于什么都不装，依赖没装，构建起跑就死。

换成干脆不传这个参数，第二次挂。命令行改口反过来问，install 填什么。打包机上没有终端，没人应答它，程序自己退了，退出码 130。

第三次把话挑明，install 就写 npm install，build 就写 npm run build。还是 22 秒挂。这回参数无可挑剔，奇怪的是无论怎么跑，命令行日志里永远没有 Install command 那一行。三挂里真正上了云构建的两次，ID 是 2608117366 和 2608120784，构建日志只有云托管控制台里能看，流水线这边一个字都拿不到。三次挂，三种死法，第三种还顺手把诊断的通道堵死了。

根因摊开来是两层。第一层，这套部署配置是 AI 写的，上一次改造之后从没在真实流水线里跑过一次，空参数、staging 这些全是按「应该这样」推出来的，今天头一回真跑，三处想象同时现形。第二层更要命，云构建的日志只进控制台，流水线里挂了也看不见它为什么挂，三次尝试全在盲跑。

解决干脆釜底抽薪，不修云构建了。构建前端这活儿打包机本来就会干，装依赖、烘配置、构建、探活一条龙，让它把成品直接推到静态托管的根目录，tcb hosting deploy 一条命令。这就是云端流水线最后一步本来要做的事，只是绕开了那个黑箱。代价是丢掉网页的版本快照，回滚从点一下变成重发旧成品。

结果当天落定。v0.26 全收官，tag 指到 adc60c01，dmg 41.6MB、exe 31.6MB 挂上 Release 和 CDN，逐字节核对过；后端探活绿；线上网页换了新入口，备案号烘进了包里，授权协议页 200。

回头看，这次的雷是 AI 埋得最安静的一种。它写的配置没有一行语法错误，跑起来也不报错，只是语义全按自己的想象来，还挑了个日志拿不到的地方死。为这一步连滚三次，GLM 的周额度烧得干干净净，教训就一条，AI 写的部署配置，上线前往真实流水线里真跑一次，推演多少遍都不算跑过。
