# client-update Specification

## Purpose

C端 桌面应用安装后能够自报当前版本、启动时与会话内每小时感知线上是否有新版本，并以全局可关闭的提示条引导用户到官网下载页或版本说明页完成更新；检测全程静默，永不打断写作。

## Requirements

### Requirement: 版本自报

C端 本地后端 SHALL 暴露版本自报能力：`v*` 标签构建的安装包在运行时 MUST 能给出构建期烘入的真实版本号；PR 构建（无版本语义）与本地开发（无烘焙文件）MUST 报 `dev` 并跳过更新检测——后者保证开发态行为与现状完全一致。版本号 MUST 来自打包期烘焙的单一来源，运行时 MUST NOT 从安装包文件名或进程路径反推。版本自报 SHALL 同时给出构建信息（分支名＋commit 短串，展示统一取前 5 位），且仅在本机版本为 `dev` 时提供：非 tag 构建从打包期烘入的构建信息键读取，本地开发态从当前 git 工作区读取；tag 构建（真实版本号）构建信息 MUST 为空，即使运行环境中存在构建信息配置。构建信息 MUST 是独立字段，MUST NOT 并入版本号本身——库文件名派生与版本比较 MUST NOT 感知构建信息。构建信息取不到时（键缺失、非 git 工作区、git 命令失败）MUST 静默回退为空，MUST NOT 影响版本号自报与更新检测。

#### Scenario: tag 构建报真实版本

- **WHEN** 用户运行 `v0.13` 标签构建的安装包并查询版本自报接口
- **THEN** 返回 `0.13`（tag 去 `v` 前缀），构建信息为空

#### Scenario: dev 环境报 dev 并跳过检测

- **WHEN** 开发者本地起 C端 后端（无烘焙文件）发起更新检测
- **THEN** 版本自报为 `dev`，更新检测直接返回"版本未知、无需提示"，不发出任何外呼

#### Scenario: 烘焙文件缺失或损坏时回退

- **WHEN** 安装包内烘焙文件缺失或版本键为空/格式非法
- **THEN** 版本自报回退为 `dev`，更新检测跳过，应用其余功能不受影响

#### Scenario: dev 环境自报构建信息

- **WHEN** 开发者在 git 工作区（分支 `main`，HEAD `f456e8fa…`）本地起 C端 后端并查询版本自报接口
- **THEN** 版本自报为 `dev`，构建信息为分支 `main` 与 commit 短串（展示取前 5 位 `f456e`），且不产生任何网络外呼与错误表现

#### Scenario: tag 构建忽略环境中杂散的构建信息配置

- **WHEN** tag 构建的安装包（版本自报为真实版本号）运行在存在构建信息配置（如环境变量残留）的机器上并查询版本自报接口
- **THEN** 构建信息仍为空，版本自报不受影响

#### Scenario: 非 tag 安装包自报烘焙构建信息

- **WHEN** CI 非 tag 构建的安装包（烘入分支与 commit）在无 git 的用户机器上运行并查询版本自报接口
- **THEN** 版本自报为 `dev`，构建信息为烘焙的分支与 commit 短串，MUST NOT 尝试读取 git

#### Scenario: 构建信息取不到时静默为空

- **WHEN** dev 运行环境既无烘焙构建信息键、也非 git 工作区（如 docker 镜像内仅复制源码）
- **THEN** 构建信息为空，版本自报仍为 `dev`，接口与界面均无错误表现

### Requirement: 启动与会话内周期检测（1 小时节流）

C端 SHALL 在应用启动后执行一次新版本检测（后台进行，不阻塞启动与界面加载），并在应用持续运行期间每 1 小时后台复查一次——长开会话（如连续写作数日）不重启也能感知新版本。真实外呼 MUST 按 1 小时节流：同一安装实例距上次真实外呼不足 1 小时（含 1 小时内重启后的启动检测与会话内复查）MUST 返回缓存结果、不再发出外呼；检测结果 SHOULD 在节流文件（`data/` 目录）记录时间戳。会话内复查判定出新版本时，提示条 MUST 在不重启应用的情况下呈现。外呼 MUST 先打主检测地址，失败（超时、连接错误或 HTTP 异常）时 MUST 按序尝试烘入的兜底地址（云托管静态托管直连域，与主地址同样过安全校验），兜底也失败才静默降级。检测的网络失败、超时或载荷格式非法 MUST 静默降级为"本次无提示"，MUST NOT 向用户呈现任何错误。

#### Scenario: 启动后静默检测一次

- **WHEN** 用户启动应用且距上次真实外呼超过 1 小时
- **THEN** 后台向版本事实源发起一次请求，启动时长与界面加载不被阻塞

#### Scenario: 1 小时节流吃缓存

- **WHEN** 距上次真实外呼不足 1 小时（1 小时内重启应用或会话内复查触发）
- **THEN** 不发出真实外呼，检测直接返回缓存结果

#### Scenario: 长开会话不重启感知新版本

- **WHEN** 应用持续运行超过 1 小时且期间线上发布了新版本
- **THEN** 下一次小时级复查判定有更新，提示条无需重启即呈现

#### Scenario: 主域故障自动切兜底

- **WHEN** 主检测地址（营销域名）请求失败，兜底直连地址可用
- **THEN** 检测经兜底地址完成并正常判定，用户无感知

#### Scenario: 网络失败静默降级

- **WHEN** 检测请求超时、无法连通或返回体版本格式非法
- **THEN** 本次视为无更新，不出现任何错误提示，下一轮检测按节流规则重试

### Requirement: 出站安全校验

更新检测的外呼目标 URL MUST 在发出请求前通过校验：仅允许 `https` 协议；目标 host MUST 命中打包期烘入的可信域集合（主下载域 + 兜底直连域，共两个），MUST 拒绝 `localhost`、环回、私有与保留地址（域名解析到内网地址同样拒绝）。校验适用于包括兜底在内的每一个候选地址。校验失败 MUST 视同检测失败静默降级，MUST NOT 发出请求。

#### Scenario: 指向私网地址的配置被拒

- **WHEN** 检测地址被改为指向内网/环回地址（含解析到内网的域名）
- **THEN** 请求不发出，检测按失败静默处理

#### Scenario: 非 https 目标被拒

- **WHEN** 检测地址为 http 协议
- **THEN** 请求不发出，检测按失败静默处理

### Requirement: 版本比较语义

版本比较 MUST 按数值段逐段比较（如 `0.10.1 < 0.11`），MUST NOT 使用字符串字典序。仅当线上最新版本严格大于本机版本时判定为有更新；相等或更小（线上回滚场景）MUST NOT 提示。

#### Scenario: 数值段比较

- **WHEN** 本机 `0.10.1`，线上 `0.11`
- **THEN** 判定有更新

#### Scenario: 线上版本不高于本机

- **WHEN** 本机 `0.11`，线上为 `0.11` 或更低（含人工回滚 latest.json）
- **THEN** 判定无更新，不提示

### Requirement: 更新提示条交互

检测判定有更新时，C端 MUST 在所有屏（含工作台沉浸模式）的全局层呈现一条 info 语气
提示条，并按自动升级链的推进呈现**三态**：

1. **准备态**（已检出更新、自动升级链尚未接手或下载中）：文案呈现「正在自动准备新版本
   v{latest}…」或带实时百分比的「正在后台下载 N%」；此态 MUST NOT 呈现手动下载入口
   （自动链正常推进期间不与手动入口并存）。
2. **就绪态**（新版本包已校验就位）：文案「新版本 v{latest} 已就绪」，主按钮为动词
   「重启更新」（点击后经确认即关闭应用进入静默安装并自动回新版），次级按钮「暂不」
   （删除就位包且该版本不再自动触发）；「查看更新内容」照旧可达。
3. **手动态**（自动链不适用——平台/本地开关关闭/发布侧总闸，或自动链停摆超过
   client-auto-update 定义的判定时限）：文案恢复「发现新版本 v{latest}（当前
   v{current}）」对照（`notes` 摘要有值时附一句更新说明），主按钮「去下载」（唤起
   系统浏览器直达官网下载页）与「查看更新内容」，以及「知道了」（关闭后对该版本不再
   出现，后续新版本重新出现——关闭记忆语义不变）。

对照文案中的当前版本号直接取自同一次检测响应，MUST NOT 发出额外请求；当前版本号异常
缺失时退回仅含新版本号的文案。就绪态横幅 MUST 独立于横幅关闭记忆：即使该版本曾被
「知道了」关闭，包就位后就绪入口仍须可见。三态之间的界面呈现延迟 MUST 不超过秒级轮询
节拍，且 MUST NOT 产生额外外呼；状态翻转 MUST NOT 触发额外的立即重拉（避免刚被用户
关闭的横幅被拉回）。无更新、检测失败或 dev 环境时 MUST NOT 呈现提示条。

#### Scenario: 准备态不给手动入口

- **WHEN** 检测到有更新且自动下载正常推进
- **THEN** 横幅呈现准备态文案（含实时百分比），不出现「去下载」

#### Scenario: 就绪态独立于关闭记忆

- **WHEN** 用户曾对该版本点「知道了」，随后包就位
- **THEN** 就绪态横幅与「重启更新」入口照常呈现

#### Scenario: 停摆才亮兜底

- **WHEN** 有更新但自动链超过判定时限未接手
- **THEN** 横幅转为兜底态并呈现「去下载」手动入口

#### Scenario: 状态翻转不重拉

- **WHEN** 用户点「知道了」关闭横幅
- **THEN** 轮询节奏变化不触发立即重拉，横幅保持关闭

#### Scenario: 有更新时提示并直达下载页

- **WHEN** 线上最新版高于本机且检测成功，自动链正常接手
- **THEN** 横幅呈现准备态（「正在自动准备新版本 v{latest}…」，下载中含实时百分比），不出现手动下载入口
- **WHEN** 自动链停摆超过判定时限
- **THEN** 横幅转兜底态；用户点击「去下载」后系统浏览器打开官网下载页，应用内不嵌套加载外部页面

#### Scenario: 查看新版本变化

- **WHEN** 横幅呈现且用户点击次级动作「查看更新内容」
- **THEN** 系统浏览器打开该版本的更新说明页（`download/v<VER>/notes.html`），应用内不嵌套加载外部页面

#### Scenario: 关闭后按版本记忆

- **WHEN** 用户对 v{latest} 的横幅点击「知道了」，应用重启后线上仍为该版本且无更新的就位包
- **THEN** 横幅不再出现；待线上出现更新版本时重新出现

#### Scenario: 无更新时不打扰

- **WHEN** 检测结果为无更新、失败或 dev 环境
- **THEN** 界面不出现任何更新相关元素

#### Scenario: 工作台沉浸态提示条不推移书内顶栏

- **WHEN** 用户处于工作台沉浸模式（/novel/* 路由）
- **THEN** 提示条以沉浸全宽变体呈现，顶栏仍固定在窗口顶端不被推走

### Requirement: 版本号常驻展示（窗口底部状态条）

C端 SHALL 在应用窗口底部常驻一条细状态条：右对齐 muted 小字展示当前版本，登录态、未登录态、工作台内均 MUST 呈现（三态无盲区），且不随路由切换消失、不提供交互。唯一豁免：免登录营销落地页（`/`）不呈现状态条——该页保留其自带品牌页脚（已含版本行），属营销页非应用态。版本文案口径：正式构建 MUST 显示「v{版本号}」；dev 构建 MUST 显示「{分支}@{commit 前 5 位}」（如「main@f456e」）——构建信息可用时 MUST NOT 渲染为「vdev」或「开发版 dev」；dev 构建构建信息缺失时 MUST 静默降级显示「开发版 dev」；版本获取失败时 MUST 静默降级显示「版本未知」。降级路径（「开发版 dev」/「版本未知」）MUST NOT 弹出任何错误提示。书架屏既有页脚版权行 SHALL 并入状态条展示；应用 MUST NOT 在状态条之外再呈现第二条底部常驻条。顶栏（常规与工作台两变体）MUST NOT 新增版本元素。

#### Scenario: 登录态书架常驻可见

- **WHEN** 已登录用户进入书架屏
- **THEN** 窗口底部出现状态条，右对齐文本含当前版本号（如「v0.15.1」）

#### Scenario: 未登录态仍覆盖

- **WHEN** 未登录用户停留在登录页或书架
- **THEN** 状态条仍呈现且含当前版本号，顶栏无任何版本元素；营销落地页（`/`）不呈现状态条

#### Scenario: 工作台内仍覆盖

- **WHEN** 已登录用户进入某本书的工作台
- **THEN** 状态条仍呈现且含当前版本号

#### Scenario: dev 构建文案

- **WHEN** 应用以 dev 构建运行（版本自报为 `dev`）且构建信息可用（分支 `main`、commit 短串 `f456e`）
- **THEN** 状态条显示「main@f456e」，不出现「vdev」与「开发版 dev」

#### Scenario: dev 构建构建信息缺失时兜底文案

- **WHEN** 应用以 dev 构建运行且构建信息为空
- **THEN** 状态条显示「开发版 dev」，不出现「vdev」

#### Scenario: 获取失败静默降级

- **WHEN** 版本获取失败
- **THEN** 状态条显示「版本未知」，且不出现任何错误提示（toast/弹窗）

#### Scenario: 书架页脚并入状态条

- **WHEN** 用户查看书架屏底部
- **THEN** 原页脚版权信息在状态条内呈现，窗口底部只有这一条常驻条

### Requirement: 控制中心面板版本行

控制中心面板 SHALL 在底部以 muted 小字展示当前版本行，文案口径与窗口底部状态条一致（正式版「v{版本号}」/ dev 构建「{分支}@{commit 前 5 位}」/ 构建信息缺失「开发版 dev」/ 失败「版本未知」）。版本获取 SHALL 静默且不阻塞面板呈现，SHALL 复用应用级版本缓存，MUST NOT 因打开面板发出额外的未缓存请求；失败时 MUST NOT 弹出错误提示。工作台本书偏好弹窗 SHALL 保留其既有底部版本行（口径不变）；本书偏好弹窗 MUST NOT 新增账号身份展示（用户名与账号徽章属控制中心面板）。

#### Scenario: 控制中心面板含版本行

- **WHEN** 用户打开控制中心面板
- **THEN** 面板底部出现版本行，文本含当前版本号

#### Scenario: 本书偏好弹窗版本行保留且不新增用户名

- **WHEN** 用户在工作台内打开本书偏好弹窗
- **THEN** 弹窗底部版本行仍出现，且不新增用户名展示

#### Scenario: 面板版本行失败静默

- **WHEN** 版本获取失败时打开控制中心面板
- **THEN** 版本行显示「版本未知」，不出现错误提示

### Requirement: 手动检查更新入口

控制中心面板 SHALL 提供「检查更新」菜单项：点击后绕过小时节流立即执行一次真实外呼
取真相（出站校验、兜底域与载荷校验 MUST 复用周期检测的同一单源）。结果以非阻塞提示
呈现三分支：有更新（含版本号对照与本机当前版本）／已最新（含渠道版本号）／渠道不可达
（给出稍后重试的补救语）。本入口的判定 MUST NOT 受横幅关闭记忆约束（手动点击＝要看
真相）；dev 构建的周期检测照旧跳过，但本入口 SHALL 照常应答（dev 排序恒最低，任何
官方版本均判更新可用，供实验构建验证入口连通性）。发现新版本时反馈文案 SHALL 明确
告知系统正在后台自动下载（衔接自动升级链）。

#### Scenario: 绕过节流取真相

- **WHEN** 用户在 1 小时节流窗内点击「检查更新」
- **THEN** 发出一次真实外呼并按最新渠道内容呈现结果

#### Scenario: dev 构建手动检查照答

- **WHEN** dev 构建点击「检查更新」且渠道可达
- **THEN** 返回渠道版本与对照结果（有更新／已最新），不因 dev 身份静默跳过

#### Scenario: 渠道不可达的补救语

- **WHEN** 手动检查时全部渠道地址不可达
- **THEN** 呈现「未能连接更新渠道」类提示并给出稍后重试出口，不呈现错误堆栈

### Requirement: 渠道自报日志

每次真实外呼成功 SHALL 在应用日志记录一行渠道事实（渠道地址、渠道版本、本机版本），
渠道全部不可达时 SHALL 记录警告级日志（含候选地址）——「客户端认的是哪个渠道」MUST
可从日志直接回答。

#### Scenario: 日志可回答渠道归属

- **WHEN** 一次真实外呼成功
- **THEN** 日志含该次实际命中的渠道地址与渠道版本
