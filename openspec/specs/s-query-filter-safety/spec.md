# s-query-filter-safety Specification

## Purpose

S端 对 CloudBase PG（PostgREST HTTP API）的查询过滤器构造安全契约：用户可控值一律按字面值等值匹配，查询操作符语义只能由服务端内部显式声明；身份/业务标识参数在入口拦截危险形态。防止把用户输入拼成过滤器表达式造成越权读取（如取得他人会话凭据）或越权改写（如批量改写他人凭据）。

## Requirements

### Requirement: 用户可控查询值按字面等值匹配

任何以用户可控字符串作为过滤值的数据查询，SHALL 将该值按字面值做等值匹配；该值 MUST NOT 被解释为查询操作符或过滤器表达式的一部分（即使其形如操作符，如 `neq.x`、`in.(a,b)`、`is.null`）。查询操作符语义（集合、比较、空值判断等）SHALL 仅通过服务端内部显式声明的通道使用，MUST NOT 依赖"值的文本形态"隐式识别。

#### Scenario: 操作符形似的设备码按字面匹配

- **WHEN** 请求 `GET /api/check-auth?pc_hash=neq.x`（未携带任何登录态）
- **THEN** 服务按 pc_hash 字面值 `neq.x` 等值查询，查无此设备，返回「等待授权」
- **AND** 响应 MUST NOT 携带任何其他设备授权记录的凭据（token）或用户数据

#### Scenario: 操作符形似的用户名不扩大匹配范围

- **WHEN** 以 `in.("a","b")`、`neq.nobody` 等形态的 username 请求登录、注册或找回密码
- **THEN** 服务按字面值等值查询该用户名，结果与查询一个不存在的普通用户名一致，MUST NOT 命中其他用户行

#### Scenario: 找回密码不会批量改写他人凭据

- **WHEN** 以 `in.("自己","他人")`、`neq.nobody` 等形态的 username 请求 `POST /api/reset_password`
- **THEN** 服务按字面值等值查询该用户名：查无此账号即拒绝（不泄露存在性差异），
  MUST NOT 读取他人行的密保答案哈希、MUST NOT 更新任何账号的密码哈希

#### Scenario: 操作符形似的订单号不越过属主校验

- **WHEN** 以 `neq.x` 形态的 order_no 请求订单详情、退款或激活
- **THEN** 服务按字面值等值查询该订单号，查无此单，返回「订单不存在」

#### Scenario: 内部显式声明的操作符查询不受影响

- **WHEN** 服务端内部以显式声明的过滤表达式执行批量查询（如按状态集合取订单、按时间窗取退款单）
- **THEN** 查询按声明的操作符语义正常生效，既有扫描/对账/补偿行为不变

### Requirement: 服务端构造的操作符表达式必须显式声明

服务端内部需要操作符语义（集合、比较、空值判断）的查询 SHALL 通过显式声明的构造方式表达；
MUST NOT 依赖"过滤值的文本形态恰好以操作符开头"来获得操作符语义——同一形态的裸字符串
（如 `eq.active`、`in.(a,b)`、`not.is.null`、`gt.<时间戳>`）SHALL 一律按字面值等值匹配。
查询的 `select`/`order`/`limit`/`offset` 参数 MUST NOT 接收请求输入。

#### Scenario: 显式声明的状态集合查询

- **WHEN** 服务端以显式声明的表达式查询 `status in (unused, active)` 的台账行
- **THEN** 出站请求的过滤值为该声明的表达式原文，集合语义生效

#### Scenario: 同形态裸字符串按字面匹配

- **WHEN** 过滤值为裸字符串 `eq.active`
- **THEN** 出站请求为 `eq.eq.active`（按字面值等值匹配），MUST NOT 被解释为 `eq.active` 语义

### Requirement: 身份与业务标识入口危险形态拦截

判定规则（分档，避免与 R1 场景冲突）：

- **用户名（登录/改密/注销/授权等既有账号路径）**：MUST NOT 做形态拦截，只依赖仓储层字面绑定——
  存量账号用户名零约束（历史注册未限制），拦截会锁人，且修复后这些用户名本可正常使用。
- **订单号 / 激活码 / 设备码 / SKU 标识 / 新注册用户名**：SHALL 做危险形态拦截——以查询操作符
  token（`eq.`、`neq.`、`in.`、`or.`、`not.`、`is.`、`gt.`、`gte.`、`lt.`、`lte.` 等）开头，
  或包含过滤器语法字符（逗号、圆括号、单双引号）的值 SHALL 被拒绝，MUST NOT 进入数据查询。

拒绝的响应形态 SHALL 沿用本服务既有约定（HTTP 200 + `{code,msg}` 业务信封，或 HTTP 4xx 但
body 同为 `{code,msg}` 信封）——MUST NOT 只返回框架默认的 `{"detail": ...}`，否则门户会把它
显示成"服务器错误"，用户看不到可行动的原因。

各参数的真实形态（拦截规则 MUST 以此为准，写死正则前先核对）：

- 订单号：`S{YYYYMMDD}-{16 位大写 hex}`（26 字符）；
- 激活码：三种并存——`O-{订单号}`（28 字符）、`TRIAL-{8 位大写 hex}`（14 字符）、
  `AC-XXXX-XXXX-XXXX-XXXX`（22 字符）；
- 设备码：C端 生成为 32 位小写 hex，但**存量数据与本地栈存在非 hex 值**（测试夹具、`hash-*` 形态），
  且门户预热会发**空串** → MUST NOT 套 `^[0-9a-f]{32}$` 白名单，只做危险形态拦截且空串放行；
- SKU 标识：取自库中配置文本，无固定形态，只做危险形态拦截。

#### Scenario: 危险形态被拒且原因是可读的

- **WHEN** 上述受拦截参数取值为操作符形似串或含 `,()`/引号
- **THEN** 请求被拒且响应体为 `{code,msg}` 信封、`msg` 指明该参数不接受的形态；
  不产生任何数据查询或写入；门户展示该 `msg` 而非"服务器错误"

#### Scenario: 合法请求零感知

- **WHEN** 既有全部合法请求形态（含含点号/连字符的合法用户名、空串设备码预热请求、
  `hash-103` 等存量设备码）
- **THEN** 行为与拦截引入前完全一致（业务错误码照旧，不得变成 400）

### Requirement: 新注册用户名形态收紧

注册入口 SHALL 要求新用户名匹配 `^[A-Za-z0-9_\-]{3,32}$`；不匹配的注册请求 SHALL 被拒绝，
并以可读文案提示合法形态（3–32 位，字母/数字/下划线/连字符；口径按 design-language §13，
不得使用"非法字符"一类机器腔）。存量账号 MUST NOT 受影响：既有用户名不匹配新形态的，
登录、改密、注销等全部功能照常可用。

#### Scenario: 新注册拒绝非法形态

- **WHEN** 注册请求的用户名含中文、空格、点号，或长度超出 3–32
- **THEN** 注册被拒，用户看到"用户名支持 3–32 位字母、数字、下划线、连字符"一类可读提示

#### Scenario: 存量账号不受影响

- **WHEN** 用户名不匹配新形态的存量账号正常登录
- **THEN** 登录成功，其名下全部功能（套餐/订单/设备/注销）行为不变
