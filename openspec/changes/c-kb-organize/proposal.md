# c-kb-organize · 知识整理（知识库二阶段⑦：AI ontology 全量维护）

## Why

知识库第一阶段（已合 main＝3c27f297）解决了「知识的存与用」：四来源入库＋建卡预填＋启用落设定＋备份往返。但知识**长歪了没人扶**——拆书一遍遍喂进来的条目之间没有关系（写法块的上下文注入缺关系依据）、同一写法以不同措辞重复入库（本轮真机实证：同一拆书角色经双出口落成两条平行条目）、概念推断放错格子（"灵力"没中词眼掉进手法）无人纠。二阶段⑦给知识库装上**维护闭环**：AI 自动做关系（可逆），内容变更一律建议＋作家确认（boss 10-31 拍板的安全原则）。

立项前完成了 ontology 建设方法的公开实践研究（Gruber 能力问题 CQ／METHONTOLOGY·NeOn·SAMOD 方法分层／Ontology Design Patterns／LLM 知识图谱构建的多阶段管线与置信分级／OOPS! 坑目录／实体消解与增量维护），吸收点全部落进 design（D1-D6），不引入新本体结构——维护在既有六概念注册表＋六类关系白名单内进行。

## What Changes

- **AI 关系整理**：拆书入库后自动一次／距上次超 7 天启动时一次／手动立即一次；一次一题材，零条目跳过。AI 产候选关系（六类白名单内）＋理由＋证据；**置信分由确定性特征合成**（证据章接近度/同题材/别名共现/概念相容——不采信 LLM 自报置信），≥0.75 直接生效、0.5–0.75 待确认不展示、<0.5 丢弃；只写 `kb_relations`，SHALL NOT 改任何条目内容；生效关系 ≤ 条目数 5 倍
- **同类合并建议**：AI 发现疑似同义条目（名字/别名/payload 槽位重合＋provenance 线索——如双出口平行条目）→ 建议合并，**作家确认**后才动数据；确认语义＝保留条目 active＋被并条目 `status=merged`＋`merged_into` 关系指向（不删行不丢数据）
- **概念纠偏建议**：AI 发现概念放错的条目（payload 形状与注册表定义错位）→ 建议挪，作家确认后走「删建」路径（concept 不可变语义不变）
- **子概念与质量标记**：AI 发现新模式建议归入某子概念（作家确认）；低质量条目标记（待清理清单，作家处置）
- **整理运行与反馈**：`kb_organize_runs` 落运行记录（模板缺失记 error 不阻断）；作家对展示中的关系点「这条不对」→ 下次整理重估；关系边进全局图（批7 全局图当前只画层级树，本变更点亮关系边渲染）
- **增量整理范围**：自动触发只做「新条目 × 既有条目」的增量对（研究结论：增量 ER 优于全量 O(n²)）；手动「深度整理」才全量

## Design Impact

- 受影响端：**C端 only**（S端不动；提示词包**新增 kb_organize 模板一枚**——LLM 产候选关系/合并/纠偏建议的唯一 AI 依赖）
- 受影响屏/弹层：
  - 知识库页：新增「整理」入口（手动立即整理按钮＋运行状态行 info/ok/warn/err 语气词）
  - 全局图：关系边渲染（六类关系色/线型区分，作家只读）；关系点击查看说明＋证据
  - 待确认清单页/弹层：合并/纠偏/子概念建议逐条「采纳/忽略」（按钮动词化）
  - 条目详情/抽屉：关系列表展示＋「这条不对」反馈钮
- 对象状态：条目新增 `merged` 状态（既有 active/archived 之外的第三态）；无新增全局组件形态
- 两端共享段：不触碰 design-system 共享段；全局图边样式沿用既有 --chart-* oklch token 六色
- 是否需要原型先行：**否**——待确认清单与反馈钮为既有列表/弹层模式扩展；全局图边渲染为既有 force-graph 数据面扩展；实现侧自查
- 设计工件：实现侧自查（文案过 design-language §13）
