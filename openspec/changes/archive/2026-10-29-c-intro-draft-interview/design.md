# c-intro-draft-interview — Design

## Context

「题材确认 → 简介」是设定向导第二步，此时系统里只有题材目录、书名、五格（可能空）。10-28 首版起草（c-intro-ai-draft）为单稿＋重掷；10-29 用户真机测试判定"只凭题材差得远"（书里旧简介/主线/世界/角色都不在输入里——从零起草设计如此），并把方向拍成：**先问几个问题、再给 3 张简介卡、作者选一张填入、自己再改**。

## Goals / Non-Goals

**Goals**
- 生成前向作者收一小口信息（三问，可全部跳过），让候选从"题材典型盘"靠近"作者心里的书"。
- 三条候选故事核真正不同，作者能"挑"而不是"重掷"。
- 交互保持单弹窗、与既有 AI 四问同风格（AI 给候选、作家挑）。
- 旧提示词包（单稿契约）不炸：后端包裹成 1 条候选平滑降级。

**Non-Goals**
- 不加"已有旧简介/主线/世界/角色"作为起草输入——起草仍是从零起稿（已有成稿的加工走润色/补缺失；那与"起草"的职责边界保持一致）。若后续需要"就着本书另写一版"，另立 change。
- 不做逐卡流式生成（一次非流式调用出 3 条，max_tokens 预算内足够）。
- 不改三件套（体检/补缺失/润色）任何口径。

## Decisions

**D1. 三问放前端、答案随请求走，后端只认 `answers`。**
问题文案是产品交互（可迭代），后端契约只关心三个字段（protagonist/taste/musts，各 ≤200、都可空）。替代案（后端生成问题）被否：问题要稳定可预期，且让模型"出问题"多一次调用、还会漂。

**D2. 一次调用出 3 条候选，不做 3 次调用。**
输出契约 `{"candidates":[{label,synopsis}]}`；后端归一：最多取 3、每条 synopsis ≤500、label ≤12（缺省「候选 N」）；temperature 0.9 拉差异、模板规则 7 要求故事核不同。三条 ≈1.5k 中文字，_JUDGE_MAX_TOKENS=4096 足够。替代案（逐条调用）被否：成本×3、延迟×3、体验无差别。

**D3. 旧模板单稿 → 包 1 条候选。**
线上提示词包可能仍是 v3（`{"synopsis"}`）——后端把非 list 形态包成 1 条（label「候选 1」）。UI 三卡渲染对 1 条天然兼容（只有一张可选）。保证"后端先发、包后发"或回滚场景都不炸。

**D4. 作者补充优先，但世界名词不许越界。**
模板 v4 规则 2：三问填了就必须用上；与题材典型盘/五格冲突时以作者为准——但规则 3（世界体系一致性）仍是硬约束（作者写"城里"也必须是该题材世界里的城）。这是 10-29 世界锚缺陷的教训延续。

**D5. 起草状态机扩为两段式（form → running → result → adopted）。**
表单作为 cards.draft 的一个普通卡（kind=text、无 adopt），复用 AiCardModal 的关闭/换一个壳；「生成 3 个候选」按钮在卡体内。候选卡接管 adopt（填入所选）与「换一个」。D9 缓存语义不变：重开同一行展示最近一批，不重复生成。

**D6. 答案与选中态用 ref 持久化在面板层。**
关弹窗不丢答案；「改一下问题」回表单时回填；换一批时选中态复位到第一条。

## Risks / Trade-offs

- 一次三候选的 token 成本高于单稿（≈3 倍输出）；但省掉"换一个"重掷的次数，总体验更省。
- 三卡并列在 520px 弹窗里较长（每张最多 500 字）——可滚动；后续如需可折叠为「标签＋前两行」。
- 若模型无视差异化规则产出三个相似故事：模板自检⑦＋temperature 0.9；前端仍有版数/换一个兜底。
