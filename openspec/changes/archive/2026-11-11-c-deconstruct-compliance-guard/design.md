# 设计：拆书合规保护闸门

## Context

见 `proposal.md` 的 Why。当前 C端 是本地优先的桌面应用：拆书原文、任务记录、知识条目都落在本机 SQLite 与数据目录；登录令牌来自 S端 OAuth，AI 功能已要求登录（`get_current_user`）。S端 已有统一调用助手 `call_server_api(endpoint, with_token=True)`（主/兜底基址、60s 冷启动口径），现有客户端端点按 `/api/...` 注册、响应信封 `{code, data, msg}`、Bearer 身份在服务端解析。C端 数据迁移走启动期幂等 DDL（`ensure_*` 模式），S端 走 alembic。

## Goals / Non-Goals

**Goals:**

- 把用户签署《拆书使用承诺》的事实升级为服务端可独立验证的记录：谁、哪版、什么时间；本机删除或重装不影响，换设备不用重签。
- 断网仍可拆书；只有"建书"这种会产生新作品的出口要求先存证。
- 导出物带 AI 辅助生成标识；原文短例与逐字引句不随出口扩散。
- 存量数据零迁移、零丢失；S端 未上线时 C端 自动降级，不把应用做成砖。

**Non-Goals:**

- 不做内容审核、不做相似度检测、不做自动改名/去标识化（后续独立 change）。
- 不在服务端保存正文、书名、作者或任何作品文本。
- 不把存证做成具有公证效力的电子签名；本设计只提供"用户确认 + 服务端留痕"的证据链。

## Decisions

### D1 一次性签署《拆书使用承诺》，不上报每次拆书

**选择**：首次拆书（或版本升级后首次）签一次承诺，服务端存一条签署记录；之后每次拆书只在本机做来源登记与确认台账，不再逐任务上报。

**理由**：承诺的条款可以覆盖"我上传的每一部作品"，一次签署即可对所有后续拆书生效。逐任务上报只会把记录量放大到与任务同量级，却不增加证据强度——真正要证明的是"用户在某时接受了这套条款"，不是"某次任务点了三个勾"。

**备选**：① 逐任务上报（拒绝：记录膨胀、字段多、隐私面大，证据收益边际）；② 只在本地记录（拒绝：本机 SQLite 可删可改，无法证明时间与不可篡改性）；③ 第三方时间戳/区块链（拒绝：成本与复杂度不成比例）。

### D2 服务端只存四个字段：谁、哪版、什么时间

**选择**：S端 记录只有 `user_id`（令牌解析）、`agreement_version`、`agreement_text_sha256`、`server_ts`（＋记录 id）。不存任务 id、书名、作者、正文、文件哈希、文件大小、设备指纹、IP、User-Agent。

**理由**：证明"用户在某时接受了某版文本"只需要这三项事实。文件哈希、来源类型、作者属于用户的阅读隐私与运营信息，放本机台账即可；传到服务端既不增加法律强度，又扩大隐私面与泄露后的影响。

**备选**：① 连文件哈希一起传（拒绝：哈希可跨库关联到具体书籍，收益小于隐私成本；本地台账已有）；② 只存 `agreement_version`（拒绝：无法证明当时看到的文本未被改，保留文本哈希成本极低）；③ 连 IP/UA 一起存进证据表（拒绝：服务端访问日志已有，不必在业务表复制一份）。

### D3 建书硬门、导出软门

**选择**：建书要求承诺「已签署」；导出允许「待同步/本机签署」但 README 与摘要标注"本机导出，承诺未取得服务端存证"。

**理由**：建书会生成一本继承原著人物与设定的新书，是传播风险最高的出口；导出是用户本机分析副本，风险次之。把硬门放在建书，既保证关键出口有签署记录，又不让离线用户失去导出能力。

**备选**：① 两个出口都硬门（拒绝：S端 抖动会让用户完全无法取结果）；② 都不设门（拒绝：签署变成"可选项"，起不到约束作用）。

### D4 服务端按「用户＋版本」幂等 + 只增不改

**选择**：S端 表 `deconstruct_consents`，`(user_id, agreement_version)` 唯一；重复签署返回同一记录；只提供 POST 与只读 GET，不提供更新/删除。

**理由**：重试与换设备是常态，幂等避免重复记录；append-only 保证证据链不被事后篡改；版本升级产生新行，旧版本保留可追溯。

**备选**：① 重复签署返回 409（拒绝：客户端要区分"已存在"与失败，复杂且易误判）；② 允许更新同一行（拒绝：证据可被覆盖，失去意义）。

### D5 原文 TTL 7 天，从终态起算

**选择**：`finished_at`（无则 `created_at`）+ 7 天；启动 sweep 删除原文目录并记 `source_purged_at`；删除任务立即删。

**理由**：7 天覆盖"拆完回头续拆/重传"的常见窗口，同时避免长期持有全文复制件。复用现有 `need_reupload` 状态，不需要新状态机。

**备选**：① 拆完即删（拒绝：失败任务无法续拆，用户要重新上传）；② 30 天（拒绝：持有期过长，收益低）。

### D6 原句证据是证据，不是内容

**选择**：`payload.field_quotes` 保留 120 字/条、500 字/卡上限；详情抽屉默认折叠；建书/用到新书/导出/分享不携带；本机备份可含。

**理由**：逐字原句的价值是让作者核对字段有没有编造，不是写作素材。把它限制在"本机、按需展开、不参与任何出口"，既保留可核对性，又切断扩散路径。

**备选**：① 让 `field_quotes` 过原文闸并要求改写（拒绝：它本来就是证据，改写后失去核对意义）；② 直接删除（拒绝：丢掉了刚建立的字段级可核对性）。

### D7 导出标识用"文末一行 + 清单元数据"

**选择**：每份 md 末尾一行显式声明；README 顶部同段；`导出清单.json` 写 `ai_generated/generator/source_book/generated_at/notice`；重复导出不叠加。

**理由**：显式声明可被读者直接看到，清单元数据提供文件级隐式标识；不加水印、不改正文，避免破坏 Markdown 的可用性。

**备选**：① 文件头加水印式标识（拒绝：打断正文阅读，且用户会手动删）；② 只写清单（拒绝：脱离清单的单文件无法识别）。

### D8 主协议加条款 + 独立附件《拆书使用承诺》

**选择**：`用户服务协议` 增补一条拆书条款，写明"拆书功能适用附件《拆书使用承诺》，附件构成本协议的一部分"；《拆书使用承诺》作为附件，首次拆书签署；隐私政策增补签署上报字段；客服页加侵权举报场景。

**理由**：主协议负责框架效力，附件负责点到点的显著同意与独立版本。若只塞进主协议：① 新增条款对已注册的老用户不生效——要么全站重签、要么老用户"没同意过"；② 条款埋在长文里，证明力弱；③ 拆书条款每次微调都要升全站协议版本，牵连所有用户。附件只影响拆书用户，版本可独立升。

**备选**：① 只写进用户协议（拒绝：全站重签或老用户覆盖不到、显著性弱）；② 新开一份独立合同（拒绝：多一套合同关系，附件已足够）；③ 只改帮助中心（拒绝：没有合同效力）。

### D9 S端 先行、C端 自适应降级

**选择**：S端 配套 change（`s-deconstruct-consent`）先落端点；C端 遇到 404 记为"本机签署"，不硬门、不阻断；端点上线后下一次重试自动转"已签署"。

**理由**：两端发布节奏独立，C端 不能假设端点一定存在；自适应降级避免"客户端先发、服务端没上"把建书锁死。

**备选**：① C端 加远端开关（拒绝：多一套配置与灰度面）；② 两端必须同批发布（拒绝：跨仓同批成本高，且回滚不灵活）。

## Risks / Trade-offs

- **[只存签署事实，被质疑"无法证明针对哪本书"]** → 承诺条款覆盖"我上传的每一部作品"；本机台账保留每次任务的来源类型、作者与文件哈希，需要时配合服务端签署记录使用；后续要更强绑定，可按版本追加文件哈希字段，不破坏旧记录。
- **[S端 长期不可达，建书一直被硬门挡住]** → 404 视为"未开通"降级；非 404 的失败给「重试同步」与「联系客服」两个出口；客服可人工核验本地签署记录。
- **[用户在本机删除数据后无法证明签署]** → 签署成功即落服务端；启动与每 10 分钟重试；换设备/重装从服务端取回；服务端保留 3 年。
- **[TTL 清理与用户续拆撞车]** → 7 天窗口 + 既有 `need_reupload` 流程 + 明确文案；任务详情提前标注到期时间。
- **[导出标识被用户手动删除]** → 标识只是一行文本，删了也不影响文件可用；清单元数据仍在；不追求技术不可移除。
- **[建书硬门降低转化]** → 仅在建书出口设门；导出仍可用；签署失败时给明确的两个出口，不让用户卡死。
- **[存证表增长]** → 每用户每版本一条，量级与版本数同级；保留 3 年，`(user_id, agreement_version)` 唯一索引即可，无需分片。

## Migration Plan

1. **S端**（配套 change）：alembic 新增 `deconstruct_consents` 表与 `POST/GET /api/deconstruct/consents`；部署到测试环境，用真实 C端 token 验证幂等、401、限流。
2. **C端**：启动期幂等 DDL 给 `deconstruct_jobs` 加 `rights_basis`、`source_author`、`source_sha256`、`source_purged_at`，新建本地 `deconstruct_consents`（用户×版本）；存量任务按「未登记」展示，不阻断查看与导出。
3. **灰度**：C端 先发存量用户，观察签署成功率与 404 比例；S端 上线后无需再发版，重试自动补齐。
4. **回滚**：S端 下线端点 → C端 下次重试收到 404 自动降级为本机签署，建书硬门自动失效；C端 回滚版本不影响已签署记录（服务端保留）。

## Open Questions

- 存证保留期最终取 3 年还是 5 年，待法务确认；当前按 3 年设计，字段与接口不受影响。
- 是否需要服务端签名回执（HMAC）以增强本机回执的可验证性；当前只存记录 id＋`server_ts`，需要时可在响应中追加 `receipt` 字段，不破坏兼容。
