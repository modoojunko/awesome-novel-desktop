# Design: c-model-list-cap-300

## Context

- `_normalize_models`（`client/backend/api_configs/service.py:40-58`）：去空白/去重保序，`truncate=False` 手动路径 >100 抛 `ValueError("模型数量过多（上限 100）")`、`truncate=True` 自动路径截前 100。上限当初防的是「百炼逾百条原样落库→后续手动 PUT 必 422」。
- 火山方舟 `/models` 实测（2026-10-24，用户真 Key）：137 条、`created` 时间升序（最老在前）；`doubao-seed-2-1-pro-260915`/`doubao-seed-evolving`/`doubao-seedream-5-0-flash-260915` 全在尾部。前 100 截断＝按供应商排序裁掉全部在役代际。
- 保头语义（默认模型置结果首位、截断时尤甚）已在实现与 spec 双钉，本次不动。
- 火山图像预设（#938 设）：头 `doubao-seedream-5-0-260128` 在 `/models` 标 `Retiring`；在役 `doubao-seedream-5-0-flash-260915`（用户正用）/`doubao-seedream-5-0-pro-260628`。

## Goals / Non-Goals

**Goals:** 上限 100→300（截断窗＋手动报错阈值同源常量）；火山图像预设头换在役 flash；spec 把 300 钉成契约。

**Non-Goals:** 不做分页/增量拉取（供应商侧无统一分页协议）；不做清单排序干预（保头已覆盖关键位；供应商原序保留其余信息量最大）；不抬到无上限（行体积与手动 PUT 边界仍需护栏）；不动百炼等其它 vendor 候选表。

## Decisions

1. **300 而非无上限**：护栏目的（防无界行膨胀＋手动路径超限 422 的确定性）保留；137 现状＋百炼/千帆增长空间留 2 倍余量。选择器渲染 300 条无压力（带搜索）。
2. **单一常量**：手动/自动两路共一个 `MODELS_MAX = 300`，报错文案同步；不存在「自动 300、手动 100」的双阈值——原拍板防的正是两路不一致造成的 422 陷阱。
3. **预设头选 flash 而非 pro**：flash 是用户实际在用的档（260915 最新批），pro-260628 面向高预算用户但作为预填默认偏重；`4-5`/`4-0` 保留兜后供手改。spec 场景文字「Seedream 5.0 系」不受影响。
4. **存量修复零迁移**：用户侧解法＝对豆包配置重测一次连接（清单全量重落）＋图像配置手改模型或重选预设；不做存量批量刷库（下次测试自然收敛）。

## Risks / Trade-offs

- 供应商未来超 300 条仍会截（保头兜底）——真发生时再议分页；300 内全量已覆盖当前所有已知 vendor（方舟 137 为最大）。
- 301+ 条手动 PUT 仍 422——语义不变，仅阈值随护栏抬升。
- 预设头换 flash 后，已按 5-0-260128 建过配置的用户不受影响（已存值不回写），仅新建预填变化。
