# c-shortfall-refill 设计

## Context

c-scene-density 已让 `done.word_check`（target/actual/below_limit）在生成链可见，但不足章的用户出路只有「重新生成」＝整章重掷（丢编辑、重烧 tokens、结果方差更大）；写侧预算（8192×thinking）与抽卡档位命中目前只能人肉观察。本件把「补足」做成确定性动作、把两个观察项做成数据。依赖 #843 的 `plot_count_hint` 与遥测字段口径，apply 排在 #843 合入后。

## Goals / Non-Goals

**Goals:** 字数不足有确定性、不毁稿的出路；截断 vs 写短可分桶；档内命中率可聚合，为写侧预算与档位表调整提供数据触发。
**Non-Goals:** 不自动重抽/自动补（一切作者触发）；不改写侧默认预算与思考超时策略（数据说话后再议）；不新增提示词模板（续写指令行走代码侧 user 素材，模板零改动）；不做命中率实时 UI（留痕可查即可，报表属后续）。

## Decisions

1. **append 续写而非整章重写**：done 已有精确 target/actual，续写＝「从尾接写到落点或下限，先到者停」是确定性最高的补法；作者编辑保留的优先级高于生成连贯性（重写毁编辑不可接受）。实现落点 apply 阶段二选一（POST /write 增 append 模式 vs 独立 /refill 端点），判据＝能否原样复用恒定层组装与 SSE 阶段流；两案均走既有保存链与分段归一。
2. **两轮封顶**：补足两轮仍低于下限＝素材/预算结构性问题，继续补只会注水——收口引导重生成，与「宁缺毋滥」的写链红线一致。
3. **遥测加列复用 TokenLog 先例**（c-llm-call-log 一族）：finish_reason 从供应商 usage 原样落列；档位命中在生成留痕时按 `plot_count_hint(target)` 与实发条数现算（同源函数即判据，不建第二套口径）。
4. **治理自查**：续写指令行是章级下限的合法表述（「已写 X 字，距下限尚差 Y——从当前局面继续写足，落点或下限先到即停」），无逐场配额；与收尾行公共串 <8 由既有钉子模式扩一条守住。

## Risks / Trade-offs

- 续写衔接质量风险（append 接缝生硬）：接缝处沿用「章首接点」同款条款思路（从最后一拍的下一动作直接写、不回顾）；实测差则回落为「保留稿＋人工续写入口」不做自动续写——数据面（补足后二改率）留观察。
- finish_reason 可得性依赖供应商回传；缺失桶单列（unknown），不与截断混计。
