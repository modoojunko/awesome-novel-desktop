# Design — 散想法入口＝主线大框

## Context

- 前端 `StoryArcForm` 的 `runAi` 恒发 `{}`（`body.input` 永远是空），所以模板里 `{input}` 槽渲染成「（无——按已填内容处理）」；而主线框（`fullstory`）内容本来就随 KV 进提示词。
- 真机实测（`real-machine-check.md`）：把散记写进主线框后起草，产出三点全部吸收、设定专名与铁律照原文用——能力已成立。缺的是**措辞口径**：块标题叫「当前主线（未填部分用（未填）标注）」，暗示"已成稿"，没告诉模型「这可能是散记、顺着扩写、关键词别丢」。

## Goals / Non-Goals

**Goals:**
- 「写进主线框就自动算输入」成为**明文口径**（提示词＋规格），并让"框里只有散记"也算足够材料。
- 接口 `input` 通道保留但降为「补充说明」，不再暗示它是散想法唯一入口。

**Non-Goals:**
- 不新增输入框、不加存储字段、不改前端（右栏描述「散着说想法也行」在本口径下由虚转实——无需改字）。
- 不改校准（本来就吃主线全文）与体检（不吃作者输入）的口径；不动 400 门槛的判定集合（措辞对齐，行为不变）。

## Decisions

**D1 提示词侧：块改名＋加一句输入口径，不新占位符。**「当前主线」→「**作者已写在主线框里的内容**（没写全很正常：可能是散想法、半成品或已成形草稿；空白处标注为（未填））」；要求句从「散想法里的关键词尽量吸收」改为「主线框里已写的内容（含散记、半成品）就是本次起草的输入——顺着它扩写，里面的关键词与显式要求尽量吸收，不要原样复述」。理由：真机已能吸收，改的是**行为可预期性**（模型不必猜"这是成稿要保留还是想法要扩写"）。
备选：把 `{input}` 槽删掉（弃：通道本身无害，留着将来若加显式入口即可用；且 spec 未删该契约）。

**D2 顺序：主线框块在前、补充说明行在后**（原顺序是散想法块在主线之前）——补充说明是附属信息，放主线框之后语义更顺；任务与 JSON 仍压尾（顺序契约的实质不变）。

**D3 不做「采纳时保留原文」的功能**：采纳·覆盖的语义（覆盖全景）不变——作者若想留原始散记，可先复制；本 change 只解决"写进框里能不能被用上"，不解决"采纳后想留底"（那需要新字段/新交互，用户已明确不要新框）。

## Risks / Trade-offs

- [模型把散记当既有成稿、只做润色而非扩写] → D1 的要求句直接点名「顺着扩写、别原样复述」；真机 A/B 复核。
- [改块标题影响别处对拍] → 已 grep 全仓确认无第二处引用「【当前主线」字样（模板独有）；测试同批断言旧标题不再出现。
- [口径回退] → 测试锁死新口径句；spec 的素材/顺序/门槛三条同批 MODIFIED。

## Migration Plan

纯提示词文本改动，无接口/存储/前端变化；随常规发版。回滚＝回退该 commit。本地/演示栈需重建 client-backend 镜像才生效。
