# c-prompt-pack-hardening — Design

## Context

现状（读代码核实）：`prompt_pack/sync.py::_install()` 把解密后的模板**以明文写盘**
（`{DATA_ROOT}/prompt-pack/v{N}/{name}.prompt`），loader（`prompts/__init__.py::_candidates/_read_verified`）
直读该目录并做读时 sha256 校验；`prompt_pack/__init__.py` 管 `pack_root/receipt/highwatermark/verify_file`。
包目录跨客户端版本共享（c-db-per-version 判例：库每版独立、包不跟），CEK 只在安装时刻使用、不落盘。

约束（来自 proposal 与用户拍板）：拼装仍在本机、离线自持不变、不引入云依赖；S端 换钥契约、
CDN 发布格式、安装包零模板断言、四态卡语义全部不变。威胁模型＝**防本机主人提取**（成本抬高型），
不承诺防内存 dump / 出口抓包 / 定向逆向（见 spec 的「本机提取防护强度与不承诺项」）。

## Goals / Non-Goals

**Goals**

- 落盘零明文：包目录里没有任何可直读、可 `grep` 的模板文本。
- 跨机不可复用：把包目录整包拷走 → 解不开（密钥绑机器+用户）。
- 不牺牲离线：装完仍可断网使用；换机/密钥失效走既有重下路径，不弹新错。
- 存量明文包可就地升级，不强迫用户重下（离线也能平滑）。

**Non-Goals**

- 不追求「本机主人拿不到」的绝对防护（原理上不可达，spec 已写死不承诺项）。
- 不动 S端 / CDN / 发布链 / 安装包硬切。
- 不做水印与溯源（阶段三备选，另立 change）。

## Decisions

### D1 落盘形态：整包单容器 `pack.bin`（AES-GCM，一次认证整包）

- 明文负载 = `{"schema":1, "templates":{name:text}}`；容器 = `nonce(12B) || ciphertext`，AAD 绑
  版本号（防容器被掉包到别的版本目录）。
- 备选①「每模板一个密文文件」：文件更多、目录里能看到模板**名字集合**（也是一点信息），且
  逐文件 nonce 管理更啰嗦 → 放弃。备选②「保持原 bundle 密文、每读一次向 S端 换钥」：破坏离线 →
  与产品承诺冲突，用户已明确否决云依赖 → 放弃。
- `manifest.json` / `receipt.json` 保留明文（不含模板内容，只有版本、哈希、签名、时间），
  便于排障与既有机制复用。

### D2 本地包密钥（LWK）：随机会话密钥 + OS 保护存储封装

- 安装时生成 32B 随机 LWK；用 OS 级保护存储封装后落 `<pack_root>/key.bin`：
  - **Windows**：DPAPI `CryptProtectData`（用户作用域，ctypes 调用，零新依赖）；
  - **macOS**：Keychain 通用口令项（`security` CLI，零新依赖）；不可用时回落「机器指纹派生
    （IOPlatformUUID + 用户 uid）」，并在日志与状态里标注为弱保护档；
  - 其他平台：同 macOS 回落档。
- 为什么要 LWK 而不是直接用 CEK：CEK 每次换版/换档都变（且不许落盘），而包目录要跨版本共享、
  离线可读 → 需要一把**只属于这台机器+这个用户**的本地钥匙。
- 为什么不落在 runtime 目录：`key.bin` 放在包目录里是自洽的（被拷走也没用），且删包重下时天然
  一起重建；密钥失效（换机/换用户/系统重装）＝按未装包处理。
- 备选「用现有 `api_configs` 的库内 Fernet 钥匙」：那把钥匙与数据同机同盘、不绑机器身份 →
  防不住「拷目录」这一主场景 → 放弃。

### D3 读路径：内存解密、零中间文件、不常驻缓存

- loader 取模板：读 `pack.bin` → 用 LWK 解密（内存）→ 取该模板文本 → 按 receipt 哈希校验 →
  返回。**不写任何中间文件**（含系统临时目录），不把整包长期缓存在内存里（按需解密；容器为
  百 KB 量级，耗时实测记入任务）。
- 备选「进程启动时全量解密常驻内存」：读写更快，但把全部模板长期摆在可 dump 的内存里，与
  「抬高成本」的方向相反、收益也小 → 放弃（按需解密 + 可选短 TTL 小缓存，默认关）。

### D4 阶段二：关键路径原生化（达到成本线的必要条件）

- 用户设定的成本线是「拿 C端 的人逆向成本 > 提示词价值」。**纯 Python 做不到**：反编译者读到
  `sync.py`/loader 后可以直接调用我们自己的解密函数。
- 因此把「解封 LWK + 容器解密」下沉到一个**编译型原生模块**（Cython/Meson 编 `.pyd`/`.so`，
  Windows 侧随 PyInstaller 打进 `_internal/`；也可用等效强度的混淆方案替代，二选一在实现时定），
  Python 侧只拿到解密后的文本。
- 备选「仅 PyArmor 等字节码混淆」：便宜，但只是拖延（解混淆工具链成熟）→ 作为弱档备选记录在案，
  默认走原生化。
- 失败即红：原生模块缺失或构建失败 → 打包流水线失败，**不得静默退回明文或纯 Python 解密**。

### D5 存量迁移：就地加密转换

- 启动补偿钩子（复用同步器既有入口）检测「包目录里有明文 `.prompt`」→ 读入内存 → 用 LWK 写
  `pack.bin` → 原子替换 → 删明文文件与旧 `manifest` 里的明文残留；全过程失败则按未装包处理
  （联网重下），**任何路径都不得退回明文可用态**。
- 迁移不改变 receipt 的 `templates` 哈希语义（仍是对模板**文本**的哈希），读时校验逻辑照旧。

### D6 卫生

- 模板文本不进日志/异常/告警；错误只带 `name`/`version`；不写 `%TEMP%` 中间件；容器解密失败
  只记 `reason=decrypt` 这类枚举值。

## Risks / Trade-offs

- [反编译者仍可读 Python 逻辑] → D4 原生化把「读源码就能解密」变成「必须逆向二进制」，这正是
  成本线所在；spec 已写明不承诺定向逆向。
- [DPAPI / Keychain 不可用] → 明确回落档 + 日志标注（不静默降级到无防护）；Windows 侧 DPAPI
  在标准用户态恒可用，风险主要在 macOS 的 Keychain 访问策略（首启可能弹一次授权，需在任务里
  验证并记录表现）。
- [原生模块构建链] → CI 与本地打包脚本各加一步编译 + 冒烟断言（模块存在且能解密自测向量）；
  构建失败即红，不做「编不出来就跳过」的软降级。
- [按需解密带来的读开销] → **实测**：341KB 容器 open 中位 15.3ms / p95 16.2ms（Python 路径；
  原生路径只会更快）。AI 调用时延以秒计，读 1~3 个模板不构成可感开销 → **不引入缓存**（D3 的
  「默认关」维持）。
- [旧明文包迁移失败] → 按未装处理、联网重下；离线用户会短暂退回「写作能力未就绪」，属可接受
  折衷（explain 在 release notes）。
- [误伤开发/测试态] → 该路径只在「已装包」分支生效；开发态仍直读包内目录，存量 e2e 零改动
  （spec 的既有 scenario 保留）。

## Migration Plan

1. 实现落地后，客户端升级首启：检测明文包 → 就地转换（D5）；`key.bin` 不存在则生成。
2. 回滚策略：本变更不改变对外契约与数据契约（receipt/manifest 语义不变），回滚旧版本时旧版
   读不到明文包目录 → 按未装处理重下（可接受）；如需完全回滚，删 `key.bin` + 重装包即可重建旧格式。
3. 发布顺序：C端 单侧发布即可（S端 / CDN / 发布链零改动）；先在内测档验证一轮（迁移 + 换机场景），
   再随常规发版放开。

## Open Questions

- macOS Keychain 首启授权提示的形态与会话保持时长（实测后回填任务清单，不影响 spec 与方案）。
- 原生模块的实现选型（Cython 直接编单个模块 vs 用等价混淆方案）在开工时按两边打包链现状定，
  两者对 spec 与任务划分无影响。
