## Context

`ai_chapter_directions`（client/backend/chapters/ai_plan.py:532-641）首调用组装两段提示词：system＝模板渲染（split_axes/plot_stages），user＝`_render(usr_t, material_blocks=_blocks_chapter(mat) + _exclude_block(exclude), position_rules=…)` ＋「请给出第 N 章的…」。结构性失败重试（589–607 行的 while 循环）却只发 `retry_system + "（上一次{cause}。）"` 与固定短句 user——素材、位置片段、目标章引导句、排除清单全部缺席（2026-10-05 实测：主调用 4091 tok vs 重试 1407 tok，重试出的卡完全脱离全书设定；该路径占历史调用近一半）。`cause` 只进重试提示词，不落日志，事后无法定位首调用为何失败。前端 `ChapterPlanModal` busy 态只有静态转圈，7–14 秒（重试时约 2×）黑盒等待。

素材装配本身健康（离线复现：⓪→⑩ 全量在包，卷纲/已拆章/人物/铁律/世界观齐备），缺陷只在重试路径丢素材。

## Goals / Non-Goals

**Goals:**

- 结构性重试的请求与首调用**同源同文**（素材包＋位置片段＋目标章引导句＋排除清单），失败原因以 system 附注形式喂回并落日志。
- 拆章抽卡 busy 态获得阶段进度（复用 `.ex-steps` 既有词汇），等待可感知。
- 后端回归钉子：任何一次方向生成请求缺素材即测试红。

**Non-Goals:**

- 不调整结构校验的松紧（约 50% 首调用失败率的成因需先积累 cause 日志数据，另立 change）。
- 不换模型/端点、不做流式输出、不回传真实后端进度事件（阶段为前端计时的感知层设计）。
- 不改提示词模板 `chapter_split.prompt` 的规则与输出契约。

## Decisions

**D1：重试 user 消息＝复用首调用组装，而非补丁式拼接。**
在端点内把 `user_msg` 的组装抽成局部函数（或先算好 `material_blocks`/`position_rules` 字符串），首调用与循环内重试都调用它；重试仅替换 system（追加「（上一次{cause}。）」）。排除清单 `exclude` 是请求内常量，循环前已算好，直接复用。
备选：只把素材块追加到重试——被否，`_render` 的占位符结构意味着绕过模板的手工拼接会与首调用漂移；复用同一组装函数让「同源同文」成为结构性保证而非纪律。

**D2：降温阶梯与重试预算原样保留。**
`retry_temp`（0.7 排除触发 / 0.3 结构性）、`MAX_ATTEMPTS = 3`、`while len(cards) < 2` 判定全部不动——spec 只封「重试带什么」，不改「何时重试、降多少温」。重试成本变化仅 +约 2.7k 字素材（对 6–14 秒的模型延迟可忽略），换来的是重试不再产出废卡、不再被排除对拍二次丢弃。

**D3：日志用模块 logger INFO 一档，不进响应。**
模块按 main.py 惯例 `_log = logging.getLogger(__name__)`；每次触发重试记一行：`retry attempt={n}/{max} cause={前两条丢卡原因或"输出不可解析"} novel={id} vol={vol_no} ch={ch_no}`。cause 已由既有丢卡提示部分呈现给作者（warnings ≤5 条口径），日志只补「尝试序号＋完整 cause」，响应形状零变化。

**D4：阶段列表＝前端计时三段，复用 `.ex-steps`。**
在 `ChapterPlanModal` 定义与 `useVolumePlan.GEN_STEPS` 同构的常量（暂名：「读卷纲与设定」「推 3 个方向」「互斥与评分自查」——终稿随原型步骤断），elapsed 阈值推进（起步值 0s/5s/10s，全段完成后保持 busy 至响应返回）。每次发起抽卡（首抽/换一批/失败重试）重置计时。渲染完全复用 `book.css` 的 `.ex-steps li / em / em.ok` 与 `ra-spin`，零新增 CSS 族。
备选：SSE/轮询真实阶段——被否，后端单次非流式调用无阶段可报，引入事件通道是另一量级的改动且 spec 明确感知层定位。
备选：照抄卷抽卡「全部进行中」静态列表——被否，四条同时转圈不传递任何进展，体感不升反降。

**D5：失败态/降级态不加阶段。**
阶段列表只属于 busy 态；出卡失败三出口、只出两套、三方向卡面维持现状（spec 四态文本仅 ① 扩写）。

## Risks / Trade-offs

- [既有测试断言裸重试行为] → `test_chapter_plan_ai_t3.py` 的重试阶梯用例可能钉过「第 2 次调用 user＝固定短句」；改断言为「含素材标记」，并同步核对 fake.calls 计数用例。
- [阶段计时与真实耗时错位（快响应走不完/慢响应停在全完成）] → spec 已把阶段定性为感知层：全完成不提前退出 busy，快响应直接换卡面；不做任何「阶段⇔后端进度」承诺。
- [e2e 桩按提示词短语匹配] → 重试 user 文案变化可能影响桩命中；落地前 grep e2e/桩文件中的索取语短语（「请给出 2 到 3 个剧情方向」），按需更新桩。
- [重试更慢（素材 ×2 请求体积）] → 仅网络与预填充成本，量级 +2.7k 字 ≈ +0.1–0.2s，远小于一次废卡重抽的代价；接受。
- [原型先行门禁] → busy 态是用户可见改动：必须先改 `book.html` 并登记 `ADJUSTMENTS.md`，再动实现，否则 `design:check` 基线不认。

## Migration Plan

无数据/API 迁移。响应形状、localStorage 抽卡会话、排除清单协议均不变；按常规 PR 合入即可，回滚＝revert 该 PR（前端阶段列表与后端重试改动互不耦合，可分提交独立回滚）。
